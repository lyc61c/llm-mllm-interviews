<a id="rag-001"></a>
### RAG-001 · 一个可落地的 RAG 系统有哪些环节？

**L1** · 腾讯

#### 答案

RAG 是检索增强生成：先从外部资料找证据，再让模型结合证据回答。它解决的是模型自身知识可能过时、缺少业务资料或难以溯源的问题。离线先解析和清洗文档，按内容切块，为片段建立索引，并保存文档 ID、页码、版本、权限和边界；在线把问题转成检索请求，召回候选、重排、组织证据上下文，最后生成带来源的回答。

例如查询公司的报销政策，检索要定位适用部门和生效日期，生成器再把金额、条件与例外讲清楚。搜索通常返回排序结果，RAG 在这些结果上进一步综合答案，所以相关性好不等于最终答案正确。上下文中也要区分用户指令与外部材料，资料里的文字不能自动变成新的执行指令。

我会分别评测“证据找到了没有”“证据是否完整”“答案是否忠于证据”，用带证据位置的样本定位失败。没有足够资料时应补检索、澄清或拒答，不能伪造引用。RAG 不等于向量数据库，也不要求一定零训练：既能直接提示已有模型，也能训练检索器或联合调整生成器。答案碰巧正确但来源不支持，仍是需要修复的错误。

#### 易错点

- 不要把 RAG 定义为必须零训练，也不要把它等同向量数据库。

#### 追问

- 怎样定位是没检索到还是模型没用好证据？

<a id="rag-002"></a>
### RAG-002 · RAG、微调与 Prompt/CoT 如何选择？VQA 中有何取舍？

**L1** · 字节跳动

#### 答案

Prompt 是给当次任务更明确的要求，思维链提示 CoT 是引导分步骤推理，RAG 是推理时补充外部证据，监督微调 SFT 则通过样本改变模型行为。我的选择依据是缺什么：事实经常更新、需要出处与权限时先看 RAG；稳定格式或重复出现的专业任务可看 SFT；输入事实充分但组合步骤容易错，可以先试问题分解与推理提示。

视觉问答中还要先区分感知、知识和推理。例如模型看不清表格小字，优先检查分辨率、裁剪、OCR 和视觉编码，继续微调或让它多想几步未必有效；图片能看懂但缺产品手册，再检索外部知识。CoT 增加 token 和延迟，也可能把最初看错的内容越推越远；RAG 会带来召回错误和图文错配；SFT 需要可信监督、域外回归，并可能遗忘其他能力。

它们可以组合，例如检索最新政策，再用微调模型按稳定格式回答和正确引用。微调不能作为能精确更新、删除事实的可靠数据库，“检索学知识、微调学能力”也只是粗略经验。我会在同一独立测试集、相同预算下比较直接回答、CoT、RAG、SFT 及组合，统计感知错误、知识缺口、推理错误、视觉幻觉和延迟，并按图片或文档来源去重。遮图、换图和输入人工 OCR 的消融能帮助确认根因，资源充足不能替代有效证据与高质量数据。

#### 易错点

- “检索只管知识、微调只管能力”是经验划分，不是严格边界。
- 提示推理、检索和微调可以组合，并非互斥架构。
- 更多资源不能替代可信监督、证据和受控对照实验。

#### 追问

- 遮图、换图和人工文字转写的对照，分别能定位什么问题？
- 知识每天更新而输出格式稳定，怎样组合检索与微调？

<a id="rag-003"></a>
### RAG-003 · chunk 大小、overlap 与父子、链式、树式索引怎样设计？

**L2**

#### 答案

切块的目标，是让一个检索单元包含足以回答的问题信息，又不过长到稀释主题或超过模型预算。我会先尊重标题、段落、表格和代码结构，再比较几组大小与重叠。Overlap 能保留边界信息，但也会增加索引和重复候选；字符数不等于 token 数，中文、英文和代码都要实际统计。

例如表格的一行离开表头和单位就无法解释，应该把这些关联信息一起保留。也可以用小块定位，再返回更大的父段；命中一个条款后补相邻段落，避免漏掉例外。链式或列表结构保存节点顺序，适合遍历或扩展邻居；树式结构用子块摘要形成父节点，逐层选择分支，但摘要可能丢掉细节，最终证据仍要回到原文。LlamaIndex 的 Summary Index 原称 List Index，默认取全部节点，不应误认为默认就是向量 top-k。

顺序、层级和向量检索可以组合。我会用有证据定位的业务样本，同时看证据召回、答案正确率、重复比例与上下文成本。大块答案更好但召回更差时，要分开检查编码截断、主题混合和缺失上下文，不能用一个固定块大小套所有文档。

#### 易错点

- 切分字符数不能自动等价为 token 数，中文与代码差异明显。

#### 追问

- 大块改善最终答案却降低召回时，怎样区分编码截断、主题混合和上下文缺失？

<a id="rag-008"></a>
### RAG-008 · HNSW 的 M、ef_construction 和 ef_search 怎样权衡？

**L2**

#### 答案

HNSW 是一种分层近邻图索引。查询先在较稀疏的上层快速接近目标区域，再到更密的下层搜索，减少遍历全库的成本；代价是它属于近似搜索，可能漏掉真正最近的向量。M 控制图的连接规模，ef_construction 控制建图时搜索得多仔细，ef_search 或实现里的查询 ef 控制在线候选搜索宽度。

增大连接或建图宽度通常能提高图质量，但增加内存和构建时间；增大查询宽度通常提高近邻召回，同时增加延迟，并要满足实现对返回 k 的约束。例如精确搜索可以找到目标、HNSW 找不到，我会先扫查询 ef，再看图构建质量，而不是立即更换 embedding。

这里要区分两种召回：相对暴力近邻的 ANN recall，检查索引是否找到应找到的向量；业务证据召回，检查这些向量是否对应真正可回答的资料。前者高不保证后者高。过滤、删除更新、距离函数和索引版本也会改变表现，因此我会在真实过滤条件与数据规模下画内存、延迟和召回曲线。

#### 易错点

- 找到精确近邻与找到业务证据是两种召回，前者高不保证后者高。

#### 追问

- 精确搜索能命中而近似索引漏掉时，先调整什么？

<a id="rag-017"></a>
### RAG-017 · IVF_FLAT、IVF_PQ 与 HNSW 如何检索，nlist/nprobe 和 PQ 有何权衡？

**L2**

#### 答案

IVF 先用粗聚类把向量分到 nlist 个倒排列表，查询选最接近的 nprobe 个簇，再搜索其中的向量。IVF_FLAT 在选中的列表中用原向量算距离，但没查的簇仍可能藏着全局近邻，所以它并不是全库精确搜索。

乘积量化 PQ 把向量分成 M 个子空间，各用有限码本编码，搜索时查表近似距离。IVF_PQ 常编码相对于粗中心的残差。N 个向量、每子空间 b 位时，纯编码约为 N×M×b/8 字节，还需加 ID、码本和其他索引开销。它同时有漏查簇和量化排序两类误差，增大 nprobe 或用原向量重排能改善，但增加成本。

HNSW 通过分层近邻图导航，通常不用先训练聚类码本，却要存更多图连接。我会按规模、内存、增删维护、训练数据代表性和召回延迟曲线选型。nlist 太大可能训练不足，nprobe 增大通常更准更慢；nprobe/nlist 只是查簇比例，列表不均匀时不能预测真实时间或召回。先做精确检索对照，再区分表示能力、粗筛和 PQ 的问题。

```math
M_{\mathrm{PQ\ codes}}\approx N\frac{Mb}{8}\ \mathrm{bytes},\qquad \mathrm{probed\ fraction}\approx\frac{n_{\mathrm{probe}}}{n_{\mathrm{list}}}
```

#### 易错点

- 倒排列表长度不均匀，nprobe/nlist 只是查簇比例，不能直接预测耗时或召回。

#### 追问

- 召回差时，怎样区分漏查簇、乘积量化误差与表示模型不合适？

### RAG-004 · embedding 模型与相似度应如何选？

**L2** · 阿里巴巴

#### 答案

Embedding 模型把问题和文档变成可比较的向量。常用双塔分别编码二者，文档可以提前算好，在线只算问题，再快速寻找近邻。选型首先看语言、领域、文本长度与模型要求的问题和文档模板，而不是直接拿一个公开榜单第一名上线。

例如产品型号、代码和跨语言问题，对表示能力的要求不同；一段很长的合同也可能被编码器截断。公开任务能用于筛候选，但还要在业务标注中测 Recall@k、MRR 和 nDCG，确认找到的是能支持答案的资料，而不只是主题相似的文字。必要时可以用对比训练和困难负例适配领域，同时排除真正相关却被误标为负例的文档。

查询和索引必须使用兼容的编码器、模板、维度与归一化方式。单位向量的余弦和内积排序一致，未归一化时未必如此；距离也不是跨模型通用的置信度。更换模型或模板通常要重编码并保留回滚版本。我会先做精确向量检索，再与近似索引对比：精确检索也失败，优先查表示；精确能找到而近似漏掉，则查索引参数。

#### 易错点

- 向量距离小不是事实正确，也不能解释为跨模型通用置信度。

#### 追问

- 怎样用精确搜索对照，区分表示模型不合适与近似索引漏召回？

<a id="rag-005"></a>
### RAG-005 · BM25 与向量检索各有什么优势？

**L2**

#### 答案

BM25 根据关键词匹配打分，综合词的稀有程度、出现频率和文档长度；向量检索根据表示相似度找语义近似内容。前者擅长型号、人名、错误码等精确表达，后者擅长用户说法与文档措辞不同的情况。两者通常互补，关键词检索并没有因为大模型出现就失去价值。

例如“退款怎么处理”可以通过语义检索找到“退货款项结算”；查询某个 SKU 或错误码时，精确字段往往更可靠，向量可能把相似型号混在一起。BM25 中 k₁ 控制词频增加到一定程度后的饱和，b 控制长度归一化，取值要结合语料验证。涉及价格区间、日期或权限时，应把这些要求转成结构化过滤，而不是全交给语义距离。

中文分词、字段配置、大小写、同义词和中英混合都会影响关键词召回，我会先查这些基础设置，再判断是否需要换模型。混合检索后要去重、重排，并分开检查关键数字、否定条件和证据支持。BM25 分数不是概率，向量接近也不等于事实正确，最终仍需真实业务评测。

#### 易错点

- 关键词检索不是必然落后，也不能用 BM25 分数当概率。

#### 追问

- 查询商品型号和价格区间时，怎样组合精确字段、结构过滤与语义召回？

<a id="rag-006"></a>
### RAG-006 · 混合检索的分数融合与 RRF 有什么区别？

**L2**

#### 答案

混合检索要把多条召回路线的结果合起来，但原始分数通常不能直接相加。BM25、余弦和不同模型分数的范围与分布不一样，一路可能因为数值大而压过另一路。可以先校准再加权，也可以采用倒数排名融合 RRF，只使用名次来计算贡献。

公式里的 d 是候选文档，L_j 是第 j 条路线的结果，rank_j(d) 是它在该路线中的排名，k 是平滑排名差异的常数。某个文档在多路都靠前，累计贡献就大；没有进入某路候选窗口，则这一项不参与。例如精确型号由关键词路找出，描述性的别名由向量路找出，RRF 能把两类候选一起保留下来。

RRF 不需要直接比较原分数，但仍要调候选窗口、排名常数和去重规则。文档应按稳定 ID 合并，窗口太小也会提前丢掉有用证据。我会按关键词、语义和多跳问题分层比较质量与 P95 延迟。融合分数不是余弦或正确性概率，所以不能沿用原来的 cosine 阈值决定拒答。

```math
\mathrm{RRF}(d)=\sum_{j:\,d\in L_j}\frac{1}{k+\mathrm{rank}_j(d)}
```

#### 易错点

- RRF 分数不等于余弦相似度或可靠性概率。

#### 追问

- 为什么融合后的分数阈值不能照搬原来的余弦相似度阈值？

<a id="rag-007"></a>
### RAG-007 · reranker 和 embedding 检索模型如何分工？

**L2**

#### 答案

Embedding 检索负责从大库快速找到一批可能有用的文档，重排器负责在这批候选中精细判断哪一些更能回答问题。双塔分别编码问题和文档，能预计算索引；常见交叉编码器把二者一起输入，让词与词充分交互，判断更细，但每个候选都要再跑模型，成本更高。

例如粗召回找到几十段退款资料，重排器可以进一步区分“退货退款”和“发票退款”，再选少量段落进上下文。重排无法补回粗召回完全没找到的证据，所以我会先测 Top-N 的覆盖，再比较 Top-K 的排序与答案效果。长文截断、多语言和分数校准也要用业务数据核查，而不是把高分自动当作可信度。

降低成本可以用候选去重、批处理、轻量排序和缓存，精排也不一定只能手工加特征权重。最终要看端到端正确率。如果相关性指标提高而答案变差，我会查是否把互补证据挤掉、遗漏限定条件、增加冗余或改变证据顺序，再用人工证据替换等消融定位问题。

#### 易错点

- 不能把精排理解成一定手工加特征权重；模型类型与任务有关。

#### 追问

- 重排的相关性分更高，最终答案却更差，应怎样排查？

<a id="rag-019"></a>
### RAG-019 · 怎样训练 embedding/retriever，hard negatives、ICT、SEED 与 REALM 分别解决什么？

**L3** · 阿里巴巴

#### 答案

训练检索器，就是让问题更接近能回答它的正例，把不相关候选拉远。双塔常用对比损失：公式中的 s 是相似度，τ 是温度，d⁺ 是正例，d⁻ 是负例。正例可以来自人工问题与证据，不能把同主题但答不了问题的段落都算进去。Batch 内其他文档作负例很便宜，却可能太容易，也可能是真正相关的假负例，需要按文档 ID、近重复和多答案标注过滤。

困难负例可从 BM25、当前模型近似检索或交叉编码器筛选获取。ANCE 用动态近似索引挖负例，RocketQA 关注跨批次负例和去噪等训练设计；困难不意味着标签可信，应混合随机负例并抽查高分误标。普通梯度累积不会自动让不同小批次互相成为负例，要扩大候选池，需显式联合打分、跨卡收集或梯度缓存。编码器更新后索引也要更新，旧索引挖出来的负例可能逐渐不贴近线上。

弱监督预训练也有不同任务：ICT 用句子与其上下文形成检索配对；SEED-Encoder 用较弱解码器形成瓶颈，促使编码器保存全局信息；REALM 把潜在文档检索纳入语言预训练。它们改变的是学习任务，不是替换数据库。之后可以混合检索、自然语言推断等监督，再用重排器分数蒸馏，采样与模板都要验证，语义相似分数高不保证检索高。

压缩要区分模型蒸馏、向量降维和索引量化。Matryoshka 显式训练多个前缀维度；用于余弦或单位范数距离时，截断后要按新维度归一化，任意模型直接截前几维没有保证。查询和文档变换必须同步，在真正压缩后的索引上测质量、速度和体积。训练评测按问题、实体或文档来源隔离，避免改写和同一答案段落泄漏。

```math
\mathcal L_{\mathrm{retriever}}=-\log\frac{\exp(s(q,d^+)/\tau)}{\exp(s(q,d^+)/\tau)+\sum_{d^-}\exp(s(q,d^-)/\tau)}
```

#### 易错点

- 未标正的文档可能仍是有效答案；困难负例也要排除同文档、多答案和近重复等假负例，否则可能损害召回。
- 普通梯度累积不会自动扩大批内负例池，扩大候选要显式联合打分。
- 未训练或验证的向量不能任意截维；模型、查询和文档变换要同步。

- 只用旧索引挖负例，为什么会越来越偏离线上候选？
- 一个问题有多个正确文档时，怎样用正例标记避免它们互为负例？
- 在相同数据与候选库下，怎样比较单任务、多任务训练和维度压缩？

<a id="rag-020"></a>
### RAG-020 · 多向量检索怎样训练和打分，ColBERT 与 ColPali 有何区别？

**L3** · 阿里巴巴

#### 答案

多向量检索保留一段文本或页面里的多个上下文化向量，而不是把全部内容压成一个向量。问题与文档分别编码，文档能离线建库，在线再做细粒度的后期交互。ColBERT 对文字 token 编码、投影并逐向量归一化；ColPali 用 PaliGemma 编码页图，再投影视觉和文本表示，与文字问题匹配，因此是检索模型，并不直接生成答案。

MaxSim 的做法是：每个问题向量 q_i，找到文档里内积最大的 d_j，再沿问题位置求和。示意来看，“发票”和“金额”各找最佳位置，得 0.9 和 0.8，总分就是 1.7；实际匹配的是上下文化向量。它是非对称的，同一文档位置能匹配多个问题词，不是平均或一一配对。普通 padding 必须屏蔽，但有效 query 扩展 token 不能一律删掉。L_q、L_d 是两边向量数，D 是维度；朴素单对成本为 O(L_qL_dD)，存储也随向量数增加。

训练时，原 ColBERT 用正负对的 softmax 交叉熵；原 ColPali 对每个问题取 batch 中最高分负例，与正例计算 pairwise softplus，即 log(1+exp(s⁻−s⁺))，不是把全部负例都放进分母的 InfoNCE。两项交叉熵与这个 softplus 等价，重要差别在负例选择。原 ColPali 主要训练语言层 LoRA 和新投影。最大值唯一时梯度可传到选中位置，并列时按实现约定处理；B 是实际联合候选池，只有一对且无其他负例时，最难负例集合为空，必须调整配置，跨卡收集合法负例则是另一回事。

大库要用候选剪枝或适配后期交互的索引，普通单向量 ANN 库不会自动支持 sum-MaxSim。投影、量化和 token pooling 能节省成本，也可能漏掉小字或表格关键格，需一起测 Recall、MRR、nDCG、P95 延迟和体积。匹配热图能帮助排查位置，却不是定位真值或因果解释；检索页图正确、生成器读错表仍应归到感知或生成环节。

```math
\begin{aligned}S(q,d)&=\sum_{i=1}^{L_q}\max_{1\le j\le L_d}q_i^\top d_j,\qquad \|q_i\|_2=\|d_j\|_2=1\\ s_k^+&=S(q_k,d_k),\qquad s_k^-=\max_{l\ne k}S(q_k,d_l)\\ \mathcal L_{\mathrm{ColPali}}&=\frac1B\sum_{k=1}^{B}\log\left(1+\exp(s_k^--s_k^+)\right)\end{aligned}
```

#### 易错点

- 普通补齐位置不能参与 MaxSim，有效的查询扩展 token 却不能一律当补齐丢掉。
- 原 ColPali 取批内最高分负例做成对目标，不能把所有批内负例的 InfoNCE 当作原损失。
- 离线编码不表示普通单向量库能直接支持多向量匹配，量化或池化也不保证排序不变。
- 只有一对问题页面且无其他负例时，最难负例集合为空，必须补合法负例或调整训练。

#### 追问

- 最大值选择为什么能反传，并列最大值时梯度怎样分配？
- 页图检索正确但生成器读错表格，属于哪个环节？
- 压缩文档向量后，怎样确认没有漏掉小字或关键单元格？

## 查询优化与图检索

<a id="rag-009"></a>
### RAG-009 · query rewrite、multi-query 和 HyDE 何时有用？

**L2**

#### 答案

查询改写解决的是用户表达与资料表达不一致。Rewrite 可以补全指代和术语，multi-query 用多种表述扩展覆盖，HyDE 则先生成一段假设性的答案文档，再用它的表示检索真实资料。比如用户说“它今年还能保修吗”，先结合对话定位“它”是哪款产品，通常比直接编码这句话更容易找到证据。

改写要保留原问题的实体、数字、否定与限定条件，并记录从历史补全的依据；多路结果再去重，避免相近说法占满候选预算。HyDE 生成的文本可能含错误事实，它只能作为检索线索，不能直接作为答案证据。真正回答时必须回到检索到的原始材料。

这些步骤也会增加调用、延迟和噪声，简单明确的 query 可能越改越差。我会保留原查询一路，在同一证据标注集上对比召回和最终答案，专门检查意图是否被改偏。例如用户问“不包含售后服务的版本”，改写不能变成“包含售后服务的版本”。收益不足时不应把改写当作必备组件。

#### 易错点

- 查询改写不是必加步骤，简单准确的问题可能被改偏。

#### 追问

- 怎样检查改写有没有改变用户的实体、数字或否定条件？

<a id="rag-010"></a>
### RAG-010 · Self-RAG 和多跳检索怎样改善复杂问答？

**L3**

#### 答案

多跳检索把复杂问题拆成依赖的证据链：先找到一个实体或关系，再根据已核实的信息查下一步。例如先查某项目的负责人，再查该负责人的机构，不能凭第一步猜到的人名继续一路检索。每一跳都应保存原文与实体关系，确认新增证据确实填补了缺口。

Self-RAG 是一个训练专用反思 token 的框架，用这些标记决定是否检索，并评价相关性、支持性等；让普通模型“自我反思一下”不等于实现它。其他自适应方式也有不同触发机制：CRAG 用检索质量判断是否纠正，FLARE 根据前瞻生成和不确定性触发检索。它们可以帮助减少无效调用，但触发器判断错了，也会漏检索或把噪声引入答案。

我会给迭代设最大跳数、token、时间和重复查询预算，并明确何时证据充分、何时停下澄清。模型自评不能当事实裁判，错误中间实体会污染后续全部步骤。除了最终准确率，还要看每跳证据覆盖；用替换或删除某跳证据的实验，检查答案是否真的依赖这条链，而不是碰巧猜对。

#### 易错点

- 模型自评不是事实裁判，错误中间实体会污染后续检索。

#### 追问

- 两跳答案正确时，怎样证明每跳证据真的被使用？

<a id="rag-016"></a>
### RAG-016 · 知识图谱 RAG 与 GraphRAG 何时有用，和多 Agent 有什么关系？

**L2**

#### 答案

知识图谱把实体、关系及来源组织起来，适合关系密集、多跳和全局归纳问题。向量检索擅长找到语义接近的原文，图结构则能沿明确关系扩展证据，两者可以结合。例如查询一家公司的子公司，可以先定位公司实体再查关系；每条关系还要能回到原文，避免抽取错误被当成事实。

Microsoft GraphRAG 会抽取图并生成社区报告。Local Search 以问题相关实体为中心扩展邻居并结合原文，Global Search 用社区摘要处理语料整体主题类问题。因此它不只是“图数据库里走几跳”。抽取可能混淆同名实体，摘要也可能遗漏或捏造信息，权限和版本都必须随证据传递。

多 Agent 是任务决策和执行的组织方式，GraphRAG 是知识组织与检索方式，一个 Agent 可以调用它，图检索也不需要多 Agent。思路图、执行图和实体知识图也不能混称。我会用关系证据召回、事实支持、实体链接、更新成本和延迟判断收益；如果只是局部事实查询，普通检索基线可能已经足够。

#### 易错点

- 思路图表示计算结构，Agent 执行图表示步骤依赖，知识图谱表示实体关系，不能混称。

#### 追问

- “公司所有子公司”与“整个行业的主要风险”分别适合哪种检索？

## 评测、权限与多模态 RAG

<a id="rag-011"></a>
### RAG-011 · RAG 如何建立分层评测并定位 bad case？

**L2** · 阿里巴巴

#### 答案

RAG 评测要按链路拆开：先看检索是否覆盖所需证据，再看上下文是否相关且完整，最后看答案是否正确、充分并忠于证据。我会准备带文档或页码定位的业务集，用人工正确证据替换真实检索，区分“没找到”与“找到了但没读好”，同时报告拒答、成本和延迟。

检索指标各看不同问题。Recall@k 是前 k 个去重结果覆盖相关集合的比例；Hit@k 只问是否至少命中一个，例如三段必要证据只取到一段，Hit 是 1，Recall 是 1/3。MRR 平均第一个相关结果排名的倒数，未命中为零。AP 在每个相关命中位置计算精确率，除以相关文档总数，MAP 再对问题平均。nDCG 用等级相关性 g_i 的收益和位置折扣评价排序，再除以理想排序的 IDCG；这里收益采用 2 的 g_i 次方减一，也有其他约定，必须固定。

公式中 Q 是问题数，T_q,k 是前 k 个去重结果的集合，R_q 在集合式中是相关集合，在 AP 中是相关数量，rel_q,i 表示第 i 项是否相关。没有相关标注或 IDCG 为零时，要先规定剔除或记零，AP@k 也要声明分母。文档、页与块的粒度不能混用，同文档多个块不能重复算多个独立命中；缺失标注也不等于真负例，多段联合证据要检查是否全部到位。

自动 judge 和无参考指标需要人工校准，记录语料、模型、提示与指标版本。公开协议只能在同条件下比较：原 MTEB 检索主要看 nDCG@10，ColPali 的原 ViDoRe 页图检索主要看 nDCG@5，语义相似任务也不能替代检索评测。业务中还要测新文档、域外样本和图表小字，并固定候选库、近似搜索与重排预算，避免总分掩盖真实瓶颈。

```math
\begin{aligned}\mathrm{Recall@}k(q)&=\frac{|\mathcal R_q\cap\mathcal T_{q,k}|}{|\mathcal R_q|},\quad |\mathcal R_q|\gt 0\\ \mathrm{MRR}&=\frac1Q\sum_q\frac1{\mathrm{rank}_q^{\mathrm{first}}},\quad \text{无命中记 }0\\ \mathrm{AP}(q)&=\frac1{R_q}\sum_{i=1}^{N}\mathrm{Precision@}i\cdot\mathrm{rel}_{q,i}\\ \mathrm{MAP}&=\frac1Q\sum_q\mathrm{AP}(q)\\ \mathrm{DCG@}k&=\sum_{i=1}^k\frac{2^{g_i}-1}{\log_2(i+1)},\quad \mathrm{nDCG@}k=\frac{\mathrm{DCG@}k}{\mathrm{IDCG@}k}\end{aligned}
```

#### 易错点

- 模型裁判和无参考指标都可能误判，需要校准，不能当作无成本真值。
- 多证据问题中，至少命中一次与覆盖比例不同；未标注相关也不等于真负例。

#### 追问

- 召回提高而答案质量不变，应该做哪些模块对照？
- 按文档、页或块计数时，怎样避免同一证据重复命中抬高指标？

<a id="rag-012"></a>
### RAG-012 · RAG 为什么仍会幻觉，怎样设计引用与拒答？

**L2**

#### 答案

RAG 仍会幻觉，因为证据可能检索错、缺少限定条件，模型也可能忽略证据或把不同资料拼成错误结论。我的做法是把回答中的关键事实绑定到具体片段，再检查片段是否真正支持这项陈述。链接能打开，只说明链接存在，不能说明该结论有依据。

例如政策写“满一年且审批通过可报销”，答案只说“满一年即可报销”，即使引用了正确页面，也遗漏了条件。索引和回答应保存资料时间、版本、页码及实际检索结果，方便回查；相互冲突的材料要确认适用范围和生效日期，证据不足时补检索、澄清或拒答，不能编出处。

评测要同时看支持率和覆盖度，避免只说很少的安全内容或空答获得漂亮分数。低温度和“仅依资料回答”的提示有帮助，但没有正确性保证。我会抽查逐项引用，并用过期资料、冲突文档和无答案问题测试拒答策略，让系统既能回答有证据的内容，也能明确说出不确定在哪里。

#### 易错点

- 低温度和“只依据资料回答”有帮助，但不保证事实正确。

#### 追问

- 两份文档政策冲突时如何选择并解释？

<a id="rag-013"></a>
### RAG-013 · 企业 RAG 如何处理权限、更新与删除？

**L3**

#### 答案

企业 RAG 的权限必须由服务端在检索和数据访问阶段执行。可信认证确定用户与租户，召回前或召回中按访问控制列表 ACL 过滤，切出的块继承原文权限和版本。不能先把敏感内容送给模型，再要求它别说，因为数据已经进入了模型上下文。

例如某合同只允许项目组访问，关键词索引、向量索引、原文读取和重排候选都要遵守同一权限。更新或删除时，也要同步原文、块、索引、缓存和权限元数据，定义允许的同步延迟与服务目标。撤权尤其要阻断旧结果继续命中，必要时先拒绝访问，再完成异步清理。

缓存键要考虑租户或用户范围、权限版本和文档版本，不能把一个人的检索结果直接复用给另一个人。我会建立跨租户、撤权、删除和更新后的验证用例，检查残余块与引用是否还能访问。权限隔离与召回质量也要一起测：过滤可能影响近似索引候选数量，但不能为了提高召回绕过授权。

#### 易错点

- 生成后再让模型过滤敏感片段太晚，证据可能已经进入上下文。

#### 追问

- 文档撤权后，如何发现并阻断旧缓存仍被使用？

<a id="rag-014"></a>
### RAG-014 · 长上下文能否替代 RAG？

**L2**

#### 答案

长上下文和 RAG 是两种提供资料的方式。材料数量可控、需要完整通读时，可以把全文放进窗口；知识库很大、更新频繁或有权限差异时，按需检索更容易控制证据与成本。两者也能组合，先找到相关文档，再让模型读较完整的内容。

能装进窗口不代表每个位置都利用得一样好。“Lost in the Middle”描述的是某些实验中，中段证据比首尾更难被用到；这是具体模型与任务的现象，当前系统还要重新验证。我会固定问题和证据内容，随机交换证据位置并控制干扰长度，看准确率随位置怎么变，把检索漏召回与模型漏读分开。

比较时使用单文档、多文档、多跳和长尾问题，固定输出预算和采样，并计入索引、prefill 和生成成本。重排、去冗余、分层摘要或分段问答都可能改善利用率，但压缩也可能删掉关键条件。结论应由真实证据覆盖、位置鲁棒性、延迟和成本决定，不能说长窗口必然淘汰检索，也不能说 RAG 在每个场景都更便宜。

#### 易错点

- 不要说长上下文必然淘汰 RAG，或 RAG 在一切场景永远更便宜。

#### 追问

- 若证据在正文中段，怎样验证模型是否漏读？

<a id="rag-015"></a>
### RAG-015 · 多模态 RAG 怎样检索图表、扫描 PDF 与视频？

**L3** · 商汤

#### 答案

多模态 RAG 不只找文字，还要找到能支持答案的图表、页面区域或视频片段。可以索引 OCR 文本、图片描述，也可以直接索引视觉表示。比如扫描报表，可以让文字检索定位公司名，再用页图或区域让生成器检查行列、表头与单位；不能因为页码找对了就断言读表正确。

ColPali 这类视觉多向量检索把文档页当图片编码，用细粒度匹配保留文字、版面和图表线索；它负责检索，不直接给出最终答案。结果应保留页码、区域和原图回链，生成时回传实际证据。视频则需先定义时间片段，保留时间戳与多帧信息：问“先发生什么后发生什么”，不能只找到一个外观相似的画面。

我会按信息类型比较 OCR 错误、视觉编码成本、文本与视觉混合召回，以及检索后生成的准确率。视觉检索可以减少部分解析依赖，但不意味着所有 OCR、结构化抽取和文本索引都能取消。失败要分层归因：找错页面是检索问题，页面正确却看错单元格是生成或感知问题，缺时间证据则要检查切段与召回设计。

#### 易错点

- 视觉检索不意味着所有 OCR、文本索引与结构化抽取都能省略。

#### 追问

- 页面检索正确、视觉语言模型却读错单元格，应该怎样归因？

<a id="rag-018"></a>
### RAG-018 · RAGFlow、Haystack、LlamaIndex 与 DSPy 怎样分工和选型？

**L2**

#### 答案

我会先列出应用需要的文档解析、元数据、检索权限、编排、评测和部署能力，再看框架。RAGFlow 偏向整合知识库接入、解析和检索应用；Haystack 用组件和 pipeline 组织检索及 Agent；LlamaIndex 提供数据、索引、检索组件，也支持工作流和 Agent。功能有重叠，不能固定说某个平台不能定制、某个库没有可视化。

DSPy 的重点是声明程序模块，再依据指标优化提示、示例或模型权重。它不是向量数据库，也不会装上就自动改进业务。优化要使用训练和开发集，独立测试集留到最后，同时计算优化阶段的模型调用成本，防止围绕一个指标过拟合。

我会用同一批困难样本做最小原型，包括扫描 PDF、中文合同、跨页表格和权限更新，检查解析、证据召回、引用、性能与故障恢复。还要确认数据能导出、版本能固定、模型和重排器能替换。升级时对照块边界与检索回归，默认示例并不代表生产质量；原型快和生产可控应各自评价。

#### 易错点

- 框架默认分块和官方示例不保证适合中文合同、扫描PDF或跨页表格。

#### 追问

- 框架升级后，怎样验证块边界、证据召回和答案没有回归？
