## 系统设计与资源预算

<a id="sys-001"></a>
### SYS-001 · 设计企业文档问答系统，先明确哪些约束？

**L2**

#### 答案

我会先明确谁使用系统、能看哪些文档、知识多久更新，以及答案质量、延迟和成本目标，再搭建企业问答链路。入口做可信认证，检索只访问权限内资料，重排后把带版本和位置的证据交给模型，最后生成可回查的引用，证据不足时澄清或拒答。

例如政策问答，不仅要查到报销条款，还要确认部门、生效时间和例外。离线解析切块应继承文档权限、ID、页码和版本，在线引用要能回到真实原文。新增、修改、删除和撤权都要同步索引与缓存，缓存键包含可见范围和版本，不能继续返回旧权限结果。

我会先用代表性文档做小基线，建立带证据的测试集，测召回、事实支持、正确率、P95 延迟和每次成功的成本，再根据失败增加图检索或 Agent。服务目标也要可测，并测试更新、拒答与跨用户访问。系统复杂度应该由实际瓶颈决定，不能在目标和权限未明确时先堆一张复杂架构图。

#### 易错点

- 架构先服务于明确目标与权限，不应在约束未清楚时堆复杂组件。

#### 追问

- 用户修改权限后旧缓存怎样失效？

<a id="sys-004"></a>
### SYS-004 · Agent 上下文溢出，怎样压缩而保持任务连续性？

**L2**

#### 答案

我会先区分不可丢的任务状态与随时可重读的材料。目标、用户约束、已确认事实、完成进度、待处理动作和失败原因保留，完整日志和长文外置成带来源版本的引用，按需找回。不能机械删最早消息，因为早期要求可能决定后续操作是否合法。

压缩可以用结构化 state、选择性保留和摘要，工具输出用分页与明确裁剪。例如一次查询返回几千条记录，当前只留下相关记录、ID 和查询范围，之后需要时再取；支付是否已成功这类状态应明确记录，不能藏在含糊摘要里。摘要中的推测与观察要区分，也不能把未知操作压成成功。

我会用长任务回放对比压缩前后的完成率、约束遗漏、证据恢复、延迟和 token 成本，并设计必须依赖早期信息的样本。摘要也可能幻觉，所以需要回链和检查。若压缩后断任务，先确认是状态丢失、检索失败还是模型没使用，再调整策略，而不是仅把窗口调大。

#### 易错点

- 机械删除早期消息可能一起丢掉用户约束与失败记录。

#### 追问

- 哪些事实必须以结构化字段保存而不能只做摘要？

<a id="sys-013"></a>
### SYS-013 · 多模态服务图片/PDF 输入成本失控，怎么优化？

**L3**

#### 答案

我会先拆开 PDF 解析、OCR、视觉编码、语言模型 prefill 与 decode 的成本，确认哪里失控，再按任务限制页数、分辨率和视觉 token。图片张数不是动态分辨率模型的可靠成本指标，同一张高分辨率页也可能产生很多 token。

例如长报告可以先检索相关页，再让多模态模型读取原图和局部区域；文字任务可结合 OCR，表格要保留表头、单位与布局。缩放与裁剪都要测细字、定位、跨页证据和最终准确率，不能一律降分辨率。预处理和特征缓存应含文件内容 hash、模型及裁剪版本，避免误复用。

我会比较每个成功任务的总成本，包含漏页后的补检索和重试。若瓶颈是视觉编码，只量化语言模型可能帮助很少；应对症减少无关页、优化批处理或预处理，再验证质量。节省 token 和 GPU 时间不能以漏掉必要证据为代价，尤其要检查跨页问题与小字图表。

#### 易错点

- 一律降分辨率可能破坏读字与精细定位，优化必须回归这些能力。

#### 追问

- 瓶颈在视觉编码而非生成时，只量化语言模型能解决多少？

<a id="sys-019"></a>
### SYS-019 · 企业 Agent 中 BFF、编排器、Tool Server 与 Worker 如何拆分？

**L3** · 米哈游

#### 答案

我会先保持清晰职责：面向前端的 BFF 管会话入口、认证和流式进度；编排器管任务状态、模型工具选择、预算与停止；Tool Server 暴露业务能力并验证权限；Worker 消费队列执行长耗时工作。小规模时可以在一个服务里保持这些逻辑边界，Worker 也可以是普通作业进程，不必全部包装成 Agent。

每次调用带可信的用户租户上下文、任务和追踪 ID，执行端再次授权，凭据由服务管理，不放进模型上下文。Checkpoint 恢复编排进度，队列通过确认和租约控制交付，业务幂等键控制重复副作用。Worker 已完成操作但回传丢失时，编排器先查操作记录，不靠重新生成一句话保证只执行一次。

我会按租户隔离数据与结果，记录版本、参数摘要、授权、耗时和真实操作状态，同时控制敏感日志。工具设置超时、有限重试、熔断、并发和取消，权限变化后重新检查排队任务与旧状态。MCP 可统一接口，却不规定这套架构，也不替代队列、审计或业务授权。验收要测成功、隔离、恢复、P95 和成本，投递保证不能直接等同于副作用恰好一次。

#### 易错点

- 网关、编排器、工具服务和作业进程是实现职责，不是 MCP 规定的固定架构。
- 队列投递与业务操作幂等不同，重试不等于副作用恰好一次。

#### 追问

- 作业进程完成操作但回传丢失，编排器怎样确认真实结果？
- 用户撤权后，排队任务与旧执行状态怎样重新授权或失效？

## 性能、缓存与并发

<a id="sys-002"></a>
### SYS-002 · LLM 服务 P95 延迟突然升高，如何定位？

**L2**

#### 答案

我会先把 P95 上升拆到具体阶段：排队、检索、prefill、decode 和外部工具，用同一 trace 关联请求与服务指标，再按输入输出长度、并发、租户和版本切片。TTFT 是首 token 前的整体等待，TPOT 是输出阶段的平均每 token 时间，不能只用一个 tokens/s 解释用户体验。

接着查变化点：到达率是否增加，长输入或长回答是否变多，活跃请求、KV 用量、缓存命中和工具重试是否变化。GPU 利用率高不必然说明有效计算多，队列和带宽竞争也可能造成尾延迟。若只某租户或新版本异常，优先检查对应配置和工作负载，而不是直接加卡。

我会提出可验证假设，用匹配长度与并发的请求回放，分别调整限流、分块 prefill、缓存或调度验证。修复后对照同一负载的尾延迟、吞吐、失败和质量，确认根因。低负载内核基准只能说明局部性能，不能充分解释线上排队；吞吐提高也可能伴随单用户更慢，需要一起验收。

#### 易错点

- 平均延迟和 GPU 利用率不足以解释尾延迟，还要看队列与请求分布。

#### 追问

- 为何吞吐上升时单请求体验可能变差？

<a id="sys-003"></a>
### SYS-003 · 如何测吞吐、并发、TTFT、TPOT，并避免错误比较？

**L2**

#### 答案

我会固定模型、硬件、精度、模板、采样、缓存和输入输出长度分布，再测到达率、完成率、并发、首 token 时间、每 token 时间和端到端延迟。请求数每秒与输出 token 每秒都要报告，因为输出更长会改变两者关系，不能只报峰值吞吐。

压测尽量由外部到达率驱动，逐步加流量看何时排队和错误急升。闭环测试若等待上一请求完成才发下一条，服务变慢时施压也自动下降，容易低估过载。要记录预热、失败、取消如何计数，并确认客户端发压和流式读取没有成为瓶颈。

我会以满足质量和延迟目标的有效吞吐选择配置，保留 P50、P95、P99 和失败率。多个实例的 P95 不能直接求平均，应从全体请求样本或可聚合直方图计算。对照实验保持同样负载与口径，缓存命中和长度变化都要声明，否则数值差异未必来自引擎性能。

#### 易错点

- 峰值 token 吞吐必须配合输入输出分布、失败口径和服务延迟目标。

#### 追问

- 如何防止闭环负载测试低估过载时排队？

<a id="sys-010"></a>
### SYS-010 · 高并发 LLM 服务如何限流与降级？

**L3**

#### 答案

我会按租户配额和输入输出 token 预算准入，同时估计 KV 容量与计算量。相同 QPS 下，长输入和长回答成本差异很大，所以不能只限请求数。队列要有长度与截止时间，饱和后主动拒绝或进入已验证的降级路径，保护正在运行的请求和重要任务。

例如过载时可减少检索候选、切到经过质量验证的小模型，或把长任务改成异步，但权限、引用和必要质量不能被绕过。长 prefill 拖住短请求时，可用分块与公平调度控制干扰。返回明确的限流或不可用错误、重试建议，并把客户端取消传到后端，避免没人接收的生成继续占资源。

我会限制多层重试和在途请求，监控主动丢弃、超时及各租户质量，用到达率压测与故障注入验证。无限排队会让全部用户都超时，降级也不是只要更快就合格；有效吞吐应该是在约束内完成的任务数，并同时检查长尾和恢复。

#### 易错点

- 过载时无限排队会让全部请求超时，应有准入与队列预算。

#### 追问

- 怎样避免短请求被长提示的读取阶段一直拖住？

<a id="sys-011"></a>
### SYS-011 · Prefix Cache 能提高多少性能，怎样设计缓存键？

**L2**

#### 答案

我会先估计可共享前缀的长度和命中 token 比例，再测缓存收益。Prefix Cache 复用完全相同前缀的 KV，主要减少 prefill，后面新生成 token 的 decode 仍要运行；短提示、少重复或长输出占主导时，端到端收益可能很小。

缓存键应覆盖前缀 token 与之前的块、模型权重、适配器和必要租户隔离。视觉输入还要识别内容和预处理版本，不能只用文件名或相同占位 token。例如公共系统提示可共享，但不同图片或 LoRA 后的同样文本不能默认共享。它缓存的是中间键值，不是最终答案。

我会分别做冷热缓存回放，记录可复用 token、首 token 时间、整体延迟和显存。保留缓存会与活跃请求 KV 竞争，需要淘汰和预算；命中率高也可能掩盖高并发排队，所以仍要看目标内吞吐和长尾。性能倍数必须来自特定负载，不能给一个脱离上下文的固定承诺。

#### 易错点

- 前缀缓存保存 KV 中间状态，不是答案缓存；适配器和图像变化也会影响复用。

#### 追问

- 公共系统提示很长、用户问题不同，哪些前缀块能共享？

<a id="sys-016"></a>
### SYS-016 · 大规模 PDF 解析怎样组合多线程、多进程与 GPU 批处理？

**L3**

#### 答案

我会把 PDF 链路拆成读文件、解码渲染、OCR 与版面、清洗切块、embedding 和入库，先测各阶段的 CPU、I/O、GPU 和队列等待。公式表示整条流水线吞吐受最慢阶段容量约束，所以增加解析 worker 未必改善最终处理速度。

一般线程或异步适合重叠网络与文件等待，进程适合 CPU 密集的 Python 计算，GPU OCR 和 embedding 集中批处理。默认带全局解释器锁 GIL 的 CPython，纯 Python 线程不能简单实现多核计算，释放锁的扩展或无锁构建另看。库安全性更优先：PyMuPDF 官方不支持多线程调用，应让独立进程各自打开文档，传路径和页范围，避免传 Document 或大页图。

结果保留内容 hash、页码、解析版本和状态，便于排序、隔离失败和重试。按文档分片较简单，超长文档可按页范围拆，但要兼顾跨页关系。Windows 的 spawn 模式要正确入口保护和初始化，传递对象要能序列化。

我会用有界队列背压，限制进程内 BLAS 或 OCR 线程，避免进程数乘线程数抢资源，也控制 GPU 模型副本数。验收看每秒成功页数、峰值资源与失败恢复，不能只追求 worker 最多；无限队列和每个进程加载一份 GPU 模型会放大内存问题。

```math
\mathrm{throughput}_{\mathrm{pipeline}}\lesssim\min_i\mathrm{capacity}_i
```

#### 易错点

- 即使有扩展库能释放解释器锁，仍不能绕过 PyMuPDF 的官方多线程限制。
- 无限队列或每个 worker 加载 GPU 模型，可能放大内存和显存峰值。

#### 追问

- 什么时候按文档分工，什么时候按页范围拆分？
- Windows 新建子进程模式下，为什么要入口保护、可序列化参数和独立初始化？

<a id="sys-018"></a>
### SYS-018 · FastAPI 与 vLLM 怎样分工，如何避免 worker 数量导致模型重复加载？

**L2**

#### 答案

我会让 FastAPI 负责应用接口、认证、校验、业务路由和流式转发，让 vLLM 负责模型执行、KV、批处理与生成调度。vLLM 已有模型服务入口，常见架构是轻量网关异步访问独立模型服务，而不是每个 HTTP 请求自己同步加载模型。

异步 Web 服务接口 ASGI 的多个 worker 是不同进程，若各自初始化模型，就可能复制权重和缓存，一启动便显存不足。所以要明确模型实例、GPU 和并行组，把网关扩容与模型副本扩容分开。客户端断连时应传取消到引擎并确认释放，限制在途请求、token 和超时，避免无接收方的生成继续占容量。

我会分开测网关排队、网络、prefill 和 decode，核对模板、停止规则、采样参数及错误码是否正确透传。async 能重叠等待，但不会让一次 GPU 前向自动加速，也不会修复同步阻塞调用。压测与断连测试能验证这种分工，吞吐最终仍由模型调度、显存和计算资源决定。

#### 易错点

- 异步接口不会自动消除同步模型阻塞，也不会避免多进程重复加载显存。
- 增加 Web worker 前，要先明确模型实例与 GPU 的分配。

#### 追问

- 客户端中途断连时，怎样确认底层生成请求也被取消？
- 怎样分别扩容无状态网关和持有 KV 状态的模型服务？

## 质量诊断与版本治理

<a id="sys-008"></a>
### SYS-008 · 如何不停服更新知识库与 Embedding 模型？

**L3**

#### 答案

我会把文档版本、embedding 模型、模板和索引 schema 绑定成一套版本，后台构建新索引，再验证文档覆盖、权限和检索质量，最后通过双读或灰度逐步切换，保留旧版本回滚。新旧编码器通常不在同一向量空间，不能只换 query encoder 继续搜旧向量。

重建期间的新文档、修改和删除需要持续补进新索引。先记录数据截止水位，再追增量，检查失败队列和数量；双写要处理事件顺序和幂等，删除标记 tombstone 防止晚到旧事件把文档复活。例如全量快照含旧合同，后来的删除也必须在切换前生效。

切换时查询编码、索引指向和缓存版本要一致，可以按租户或请求分桶灰度，再原子切换指向。我会回放同一问题比较召回、引用、权限与延迟，并演练回滚及增量追平。只确认索引建成还不够，遗漏更新和旧权限结果同样会导致上线问题。

#### 易错点

- 只换问题编码器不重建文档向量，可能把不同向量空间错误混用。

#### 追问

- 全量重建期间新增文档怎样补到新索引？

<a id="sys-009"></a>
### SYS-009 · RAG 回答错了，怎样区分检索错误与生成错误？

**L2**

#### 答案

我会先保存问题、正确答案、召回候选、最终上下文和回答，确认知识库里有没有足够的正确证据。然后用人工确认的证据替换检索结果：仍答错，优先看生成器、模板、感知或推理；变对，则继续查切块、召回和重排。

对照需要尽量保持上下文预算与提示一致，避免人工证据更短更清晰导致归因混杂。多跳问题要定义所有必要关系是否覆盖，不能只命中一个段落就算证据充分。我会分别记录未召回、证据冲突、裁剪丢条件、引用错配和不忠实生成。

再通过控制模块的实验验证假设，例如用精确检索检查近似索引，用固定候选检查重排，用原图检查 OCR。增大 K 可能提高覆盖，也可能塞入噪声，所以同时看证据召回、支持和答案正确率。端到端分数能发现问题，却不能单独定位根因，所有错误都叫幻觉也会妨碍修复。

#### 易错点

- 不能把所有错误都叫幻觉，增大候选数也可能引入更多噪声。

#### 追问

- 多跳问题怎样定义“足够证据”？

<a id="sys-012"></a>
### SYS-012 · 微调上线后质量衰减，如何诊断数据漂移？

**L3**

#### 答案

我会先确认线上权重、模板、tokenizer、输入处理和工具版本是否与验收一致，再判断是不是数据漂移。按领域、语言、长度、时间和用户类型切片，抽查新错误，并在旧模型上回放同一批输入，区分分布变化、接口退化和微调遗忘。

例如新用户输入更长、图片更小，质量下降未必靠多训练几步解决；聊天模板变化也可能让模型表现异常。没有实时标签时，可以监控输入分布、拒答、工具失败与反馈作为线索，但这些代理信号不等于正确率，仍需要有针对性的人工标注。

我会用符合上线时间的独立集验证，避免同来源泄漏，再决定回滚、修配置或补数据。新数据微调后，既看新问题是否改善，也回归旧能力并灰度比较延迟和成本。训练 loss 不能代替这些检查，增加步数也不能修复版本和服务链路错误。

#### 易错点

- 质量退化先查服务配置和数据变化，不应直接增加训练步数。

#### 追问

- 无实时标签时可用哪些代理信号，局限是什么？

<a id="sys-014"></a>
### SYS-014 · Prompt 优化“修好一类坏了另一类”，怎样控制回归？

**L2**

#### 答案

我会把 prompt 当版本化配置管理，保留按业务、能力和历史错误分层的回归集，再加未用于调参的新鲜验证集。修复某类错误前明确目标收益与可接受回归，修改后看各组，而不是只看平均分或那几个新坏例。

例如增加“回答要简短”可能改善客服体验，却让复杂合同条件缺失，应该按任务检查是否需要局部路由或专门示例，而不是继续加互相冲突的全局要求。模型、工具 Schema、模板和采样要完整记录，尽量控制一次只改一个因素，才知道变化来自哪里。

我会先归因再决定改 prompt、数据还是模型：格式歧义可改提示，缺证据要修检索，稳定能力缺口可能需要数据训练。最后盲评和灰度验证质量、延迟与成本。固定测试集反复被调过就不再独立，要持续留新集验收，防止修完题库却损害真实任务。

#### 易错点

- 只验证新坏例而不跑历史回归，容易修好一类、损害另一类。

#### 追问

- 怎样根据错误根因决定改提示、数据还是模型？

<a id="sys-005"></a>
### SYS-005 · 工具调用失败后如何重试，怎样避免重复副作用？

**L2**

#### 答案

我会先判断工具失败是瞬时故障、业务错误还是结果未知。业务上参数不合法通常不能靠重复调用解决；超时则可能已经执行，特别是支付、发消息和创建对象，应先查询既有状态，再决定是否重试。

写操作使用同一业务意图的幂等键，服务端检查重复键的参数是否一致并保存结果。例如响应丢失后仍用原键回查，不能新建一个键再支付。执行、幂等记录与状态更新要可靠协调，取消等待不代表远端取消，要最终回传已提交或未知的真实状态。

我会设置全局截止时间、有限次数、退避、并发上限与熔断，防止应用、网关和工具各自重试造成放大。只读重试也消耗资源，要受预算限制。验收用响应丢失、迟到结果和重复投递的故障注入，检查副作用是否重复，不能只相信模型说不会再执行。

#### 易错点

- 所有异常都重试，可能造成重复副作用和重试风暴。

#### 追问

- 如果客户端取消但服务端已提交，怎样反馈最终状态？

<a id="sys-006"></a>
### SYS-006 · 设计 Agent 可观测性：日志里应该记录什么？

**L2** · 米哈游

#### 答案

我会用 run_id 或 trace_id 串起一次 Agent 任务，把模型、检索、规划和工具调用记为关联 span，也就是每个调用阶段的追踪记录，保存版本、耗时、状态、错误和终止原因。异步子任务保留父子关系，跨服务传追踪上下文，这样才能从最终错误回到导致它的那一步。

记录应包含足够的输入摘要、检索证据版本、调用参数与实际结果，区分模型填错参数、工具执行失败和环境异常。例如任务没完成，可能是上游检索漏了政策，也可能是退款接口超时，仅一个错误堆栈看不出来。成功状态、token、调用和费用也要记录，才能判断是否有效推进。

我会对敏感字段脱敏并限制权限与采样，避免日志成为数据泄露通道。回放优先用工具快照或模拟结果，写操作不能直接重放到生产；外部状态有变化时注明边界。最后以真实任务失败和故障注入检查追踪是否足够定位，而不是仅看日志量多不多。

#### 易错点

- 只有末尾错误堆栈，没有中间状态和版本，往往无法回溯根因。

#### 追问

- 如何定位模型生成错误与工具返回错误？

<a id="sys-007"></a>
### SYS-007 · 多租户 RAG 如何保证权限隔离？

**L3** · 米哈游

#### 答案

我会从可信认证取得租户和用户身份，再在检索端按文档 ACL 限定候选，必要时返回前复核授权。用户自己传的 tenant_id 不能直接当身份，提示里的保密要求也不能替代服务端检查。

向量、关键词、重排、原文读取、引用和缓存都要带同一访问范围。例如混合检索里向量路做了过滤，关键词路没做，敏感正文仍可能进上下文；只隐藏链接已经太晚。缓存包含权限范围或版本，撤权后失效，多轮历史中的旧引用也要重新检查。跨租户共享前缀或答案，要评估内容与时间侧信道。

我会建立跨租户、撤权、删除和各检索分支的测试矩阵。过滤使召回下降时，在该用户有权访问的相关集合上重测 Recall@K，检查候选不足与索引策略，不能通过放松权限提高数字。权限隔离、召回和缓存性能必须一起验证，授权边界始终由可信执行层控制。

#### 易错点

- 先全库检索再隐藏链接不够，敏感正文可能已经进入上下文。

#### 追问

- 加权限过滤后，怎样在该用户有权访问的证据集合上评价召回？

<a id="sys-015"></a>
### SYS-015 · 线上模型事故如何止损、回滚与复盘？

**L3**

#### 答案

我会先按用户影响止损，切回已验证版本、限制故障路径或暂停危险写操作，同时保全日志和配置快照。回滚是整条链路的事情，权重、tokenizer、模板、索引、适配器和工具 Schema 都可能相关，不能只退模型文件。

发布前就要定义触发阈值与回滚兼容性。如果旧版不能读新状态或数据 schema，应先有兼容迁移、双版本读取或明确的恢复方案，不能事故后盲切。止损同时确认已发生的副作用，回滚服务不会自动撤销退款或发送记录。

复盘时我会建立时间线，用切片和回放区分触发因素、根因与放大因素，例如一次工具变慢被多层重试放大。把结论转成回归样本、监控和演练，再验证能否拦住同类事故。报告用证据说明影响与措施，不把个人责备或未经验证的数字当根因分析。

#### 易错点

- 只退权重可能漏掉同时变化的分词器、模板和索引。

#### 追问

- 新旧数据结构不兼容时，怎样设计可执行的回滚？

<a id="sys-017"></a>
### SYS-017 · 个人多模态记忆怎样存储、检索、更新并处理相互矛盾的信息？

**L3**

#### 答案

我会把当前会话状态和跨会话记忆分开，原图、音视频存对象存储，转写、摘要和描述用于检索，结构化记录保存用户、来源、时间、区域或片段位置、内容 hash、置信度及版本。向量索引只负责找相似内容，不能作为唯一事实库，也不能证明身份或图里的事实。

长期记忆还要区分偏好、具体经历和任务状态，查询先按用户权限、有效时间及类型过滤，再做文本与模态混合召回和重排。只注入当前相关证据，可以结合相关性、时间与重要性排序，但权重需真实任务校准。例如现在问地址，应取当前有效地址，旧旅行经历中的住址不能因为相似度高就压过新记录。

写入先核验、去重并留证据，用户搬家时终止旧地址的有效期，保留历史经历但不当当前事实；冲突记录明确待确认，不把模型猜测写成稳定记忆。纠正和删除要同步派生摘要、向量与缓存。评测覆盖时间正确、跨会话召回、错误写入和隔离，并用正确证据替换区分检索失败与模型忽略。

#### 易错点

- 视觉向量相似不证明图里事实正确，也不能直接确认用户身份。
- 模型推测不能写成稳定事实，更新原记录也要处理旧摘要、向量和缓存。

#### 追问

- 用户说“我搬家了”时，事实的时间有效性和旧经历应怎样分别保留？
- 怎样区分检索不到正确记忆与正确记忆被模型忽略？
