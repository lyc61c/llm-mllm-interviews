## KV Cache 与服务调度

<a id="inf-001"></a>
### INF-001 · KV cache 缓存什么，为什么通常不缓存历史 Q？

**L1** · 腾讯

#### 答案

KV Cache 就是把历史 token 在每一层产生的键 K 和值 V 存下来，让模型生成下一个 token 时不用重新算整段历史。Q 是查询，K 用来判断历史位置与当前查询的相关程度，V 提供被加权汇总的信息。输入阶段先并行处理提示词，建立缓存；生成阶段只为新位置计算 Q、K、V，把新的 K、V 追加进去，再用当前 Q 查询全部可见历史。

通常不存历史 Q，是因为历史位置的注意力输出已经算完了，后续位置只需要自己的 Q 去匹配历史 K。比如生成“北京的天气”时，算“天气”这个位置仍要读取“北京的”的 K、V，却不需要再计算这些旧位置的查询结果。

这个复用成立的关键是因果注意力：新增内容不会改变旧位置的表示，双向注意力一般不满足这一点。它节省重复计算，但以额外显存为代价，也没有把每步注意力变成常数复杂度，历史越长，读取的 K、V 越多。更换模型权重、LoRA 适配器、前缀或位置编码设置后，都要检查旧缓存是否还有效。

![自回归解码的 KV Cache 追加与复用](../assets/kv-cache.svg)

第 4 个位置新增 Q/K/V，复用已有 K/V，并输出第 5 个 token 的概率分布。

#### 易错点

- KV 缓存减少历史重算，但新查询仍要读取历史键值，每步注意力不会变成常数成本。
- 缓存是以显存换计算，不能说用了缓存就降低总显存。

<a id="inf-002"></a>
### INF-002 · 怎样估算推理权重、KV cache 与总显存？

**L2**

#### 答案

我会把推理显存分成权重、KV Cache、激活和算子工作区，再加框架预留，而不是只看模型文件大小。权重的第一步估算是参数量乘每参数字节数。70 亿参数用 FP16 或 BF16，纯权重约 14 GB，也就是 13.0 GiB；14B 模型约 28 GB，26.1 GiB。换成 INT8 时纯量化码约减半，但还有缩放系数、未量化模块和运行开销，不能据此说一张 14 GB 卡就能运行 14B 的完整服务。

KV 的公式是两份缓存乘并发数、层数、长度、KV 头数、每头维度和元素字节数。式中 B 是并发序列数，L 是层数，T 是已缓存长度，H_kv 是键和值的头数，d_h 是每头维度，s 是字节数。32 层、32 个 KV 头、头维 128、4096 长度的单序列 FP16 缓存是 2 GiB；改成 8 个 KV 头则为 0.5 GiB，所以不能拿查询头数代替 KV 头数。

长度不同的请求要按各自长度求和，视觉 token 也计入可见序列。多卡时还要确认缓存究竟被切分还是复制，分页尾块、量化元数据、对齐和碎片都会影响实占。最后我会实测长输入和接近最大输出长度的峰值，因为加载成功不代表服务能承受并发。缩短窗口、降低缓存精度或限制准入能控制容量，但必须同时检查质量，特别是上下文裁剪会直接改变模型能看到的信息。

```math
M_{\rm KV}\approx2BLTH_{\rm kv}d_hs
```

#### 易错点

- GB 与 GiB 的单位不同，估算与实测要统一口径。
- GQA 缓存按键值头数计算，不能套用多头注意力的查询头数。
- INT8 纯权重大小不等于服务总显存，更不等于训练所需状态大小。

#### 追问

- 视觉 token 怎样计入缓存长度？
- 为什么四位权重文件大小不等于运行时显存？

### INF-003 · MHA、MQA 与 GQA 的结构、KV 显存及速度有何差异？

**L1** · 腾讯 / 阶跃星辰

#### 答案

这三种结构的区别，是多少个查询头共享一套键和值。多头注意力 MHA 中，每个 Q 头各有自己的 K、V；多查询注意力 MQA 中，所有 Q 头共用一套 K、V；分组查询注意力 GQA 则把 Q 头分组，每组共享一套。Q 头仍各自计算相关性，并不是先把 Q 平均掉。均匀分组通常要求查询头数能被 KV 头数整除。

张量可写成 Q:[B,H_q,L_q,d_h] 和 K/V:[B,H_kv,L_k,d_h]，B 是批大小，H_q、H_kv 是两类头数，L_q、L_k 是查询和历史长度，d_h 是头维度。第 i 个 Q 头与它所属组 g(i) 的 K 做相似度，再汇总该组 V，最后拼接各头输出。公式中的 N 是层数，T_total 是所有请求的缓存 token 总数，b 是每元素字节数。把 32 个 KV 头降到 8 个，理论 KV 容量降为四分之一；查询、输出投影和大部分前馈网络并不会一起降为四分之一。

共享 K、V 尤其能减少生成阶段的显存读取，但实际提速还取决于批大小、上下文和内核。实现最好直接映射共享头，显式复制 K、V 可能抵消收益；张量并行卡数超过 KV 头数时，也可能需要复制缓存，不能继续理想均分。已有 MHA 模型可按组聚合 K、V 权重再补充训练，直接平均上线没有质量保证。选 GQA 或 MQA 时，我会一起验证任务质量、长上下文表现和真实服务延迟。

```math
\begin{aligned}M_{\rm KV}&\approx2NT_{\rm total}H_{\rm kv}d_hb\\O_i&=\mathrm{softmax}\!\left(Q_iK_{g(i)}^\top/\sqrt{d_h}\right)V_{g(i)}\\H_q\bmod H_{\rm kv}&=0\end{aligned}
```

#### 易错点

- GQA 共享键值头，并非把全部注意力头都减少；实现也可能发生物理复制。
- KV 头数减少的比例，不能直接预测整体延迟、训练计算量或质量变化。

### INF-004 · prefill 与 decode 各在做什么，瓶颈为何不同？

**L2**

#### 答案

Prefill 是模型读取完整提示词、建立历史 KV 缓存的阶段，decode 是利用缓存逐步生成后续 token 的阶段。Prefill 中不同输入位置可以并行计算，线性层通常形成较大的矩阵乘法；稠密注意力还包含输入长度的二次项。Decode 常常每个请求每轮只增加一个位置，这个新查询仍要读取越来越长的历史 K、V，注意力计算量大致随历史长度 T 和特征维度 d 线性增长。

例如一次输入几千字、只回答一个词，时间主要可能花在 prefill；输入很短、回答很长，则会反复经历 decode。小批量 decode 往往没多少算术工作，却要搬运大量权重和缓存，所以容易受显存带宽限制；prefill 往往更能利用算力。这是常见趋势，不是所有硬件和负载都如此。

我会先用性能分析器看时间花在矩阵计算、权重读取、KV 读取还是内核启动上，再决定量化、算子融合和调度方案。扩大 batch 能让多个请求分摊权重读取，但也会提高显存占用和排队时间。分块 prefill 可以减少长输入对正在生成请求的干扰，效果要用固定输入输出长度分布、首 token 延迟和每 token 延迟验证，不能只比较总 tokens/s。

#### 易错点

- Prefill 常偏计算、decode 常偏带宽，但瓶颈会随负载与硬件改变。
- 比较 token 吞吐时，必须说明输入和输出长度分布。

#### 追问

- 把长提示分块处理，为什么能减少对正在生成请求的干扰？
- 怎样用算力与带宽上限的对比，判断量化是否可能加速？

### INF-006 · PagedAttention 与 FlashAttention 解决的问题有何不同？

**L2**

#### 答案

PagedAttention 主要解决生成服务中 KV 缓存怎么分配和共享的问题。每个请求的最终输出长度未知，如果预先给它留一大段连续显存，容易浪费并产生碎片。分页方法把缓存分成固定大小的块，用块表把逻辑顺序映射到不连续的物理显存，随着生成按需增加块，注意力内核根据块表读到正确的历史 K、V。

例如两个请求共享同一段提示词，可以共享对应缓存块；它们之后生成不同内容时，再各自分配新块。引用计数用来判断共享块是否还在使用，需要修改共有块时可以采用写时复制，避免一条分支覆盖另一条分支的数据。块越大，最后未填满的空间可能越多；块越小，映射和管理成本也可能提高。

FlashAttention 解决的是注意力计算过程中的中间矩阵和读写，PagedAttention 解决的是缓存管理，所以可以配合。分页不会减少同样一组 K、V 所含的元素数，也不能让单请求无限增长。高并发仍要设置容量、准入和抢占策略。性能判断应结合实际长度分布与尾延迟，不能把论文中的特定吞吐倍数当成所有部署的保证。

#### 易错点

- 分页改善分配浪费，但缓存仍占显存，单请求不能无限增长。
- 论文中的特定吞吐倍数不能直接承诺到其他服务负载。

#### 追问

- 块大小怎样影响末块未填满的浪费？
- 分支生成修改共享块时，为什么可能需要写时复制？

### INF-007 · continuous batching 与普通 dynamic batching 有何区别？

**L2**

#### 答案

连续批处理的核心，是在每一轮生成结束后重新组织正在运行的请求。普通动态批处理通常先把到达时间接近的请求拼成一个批次，再处理；生成长度不同的话，短请求结束后空出的计算位置可能要等整批结束。Continuous batching 可以每轮移除已完成请求、加入新请求，让空位更快复用。

比如一批里有人只要几十个 token，有人要几千个，连续批处理能在短回答结束后接入新用户。但新请求先要读提示词，长 prefill 可能拖慢旧请求的下一轮 decode，因此还需要单轮 token 预算、分块 prefill 和公平性策略。最大请求数与每轮 token 数是两种约束，前者管序列数量，后者管当轮工作量。

它不是始终拼最大的批次。批越大可能吞吐越高，也可能让排队、每 token 间隔和 KV 占用恶化。我会固定请求到达率、输入输出长度分布和延迟目标，逐步加负载，比较满足目标的有效吞吐、失败率与 P95/P99 延迟。长请求是否被饿死、短请求是否被长输入拖住，都需要单独观察。

#### 易错点

- 连续批处理每轮重新安排请求，并非永远运行最大的批次。
- 峰值吞吐要和排队、尾延迟一起看。

#### 追问

- 怎样避免短请求被长输入或长回答拖慢？
- 批大小上限与每轮 token 预算分别约束什么？

<a id="inf-014"></a>
### INF-014 · prefix caching 与普通 KV cache 有何区别？

**L2**

#### 答案

普通 KV Cache 是同一个请求生成时复用自己的历史；前缀缓存是多个请求共享完全相同前缀的 KV，主要省掉重复读取提示词的计算。例如客服请求都先带同一段系统说明，第二个请求命中这段前缀后，可以从新问题处继续 prefill，而不是把公共说明再算一遍。

判断能否共享，必须基于 token 和它之前的完整上下文。相同句子放在不同历史后，表示可能不同，所以缓存键要串联父块信息，并考虑模型权重、LoRA 适配器和相关预处理。多模态中，占位 token 相同但图片不同也不能共享，应把图片等内容纳入识别。语义接近的改写只能帮助其他缓存策略，不能据此复用精确 KV。

缓存块会占显存并与活跃请求竞争，需要淘汰和容量策略，换权重或适配器要失效或隔离。多租户还要考虑权限与响应时间侧信道。把稳定公共内容放在前面通常更容易命中，但并不加速新生成 token 的全部 decode。测收益时应说明冷热缓存和前缀命中率，避免把缓存状态差异误当成框架性能差距。

#### 易错点

- 缓存键要包含前缀上下文，不能只对当前局部文本取哈希。
- 前缀复用主要省 prefill，不能加速全部后续生成计算。

#### 追问

- 公共系统提示放在最前面，为什么更容易命中？
- 多适配器和多租户怎样隔离缓存？

<a id="inf-015"></a>
### INF-015 · 如何同时优化 TTFT、每 token 延迟与吞吐？

**L2**

#### 答案

我会先把三个指标分清：TTFT 是用户发出请求到收到首个 token 的时间，包含排队、prefill 和传输；ITL 是相邻输出 token 的间隔；吞吐是单位时间处理的请求或 token 数。首 token 很快不代表整段答案快，后台内核很快也不代表用户实际收到得快。

优化时先固定请求率、输入输出长度分布、缓存状态和质量配置，再测客户端与服务端各自的 P50、P95、P99、失败率和资源占用。长输入拖慢首 token，可以考虑前缀复用和分块 prefill；输出间隔过大，就看 batch、权重和 KV 带宽、内核启动及请求间竞争。扩大 batch 往往提高利用率，但也可能增加排队和每轮生成的耗时。

我会逐步提高到达率，画出延迟与有效吞吐的变化，找出饱和点，再选择满足服务延迟目标的配置。这个有效吞吐也叫 goodput，即符合目标的产出；离线最大 tokens/s 不能代替它。输入 token 和输出 token 的吞吐要分开报告，低并发与高并发也未必用同一参数。每次改调度或缓存后，都要回放同一负载，确认没有把平均值改善换成更差的长尾体验。

#### 易错点

- 首 token 快不代表整段回答快，还要看后续输出间隔。
- 输入与输出吞吐不能混用，比较时要说明长度分布。

#### 追问

- 低并发与高并发适合使用相同调度参数吗？
- 前缀命中率不同，会怎样影响压测比较的公平性？

<a id="inf-016"></a>
### INF-016 · Decoder-only 批量生成为什么通常左 padding？右 padding 一定不可以吗？

**L2**

#### 答案

批量生成常用左侧补齐，是为了让每条样本最后一个有效 token 都位于张量末尾。很多 Transformers 生成循环直接取末位 logits 来预测下一词：若右侧补齐，短样本的末位实际是 PAD，取到的是 PAD 查询位置的输出，未必是原文本最后有效位置的预测。

注意力掩码通常解决“哪些位置可被当成键读取”，不会自动把取 logits 的索引改成最后有效位置。比如一条输入三词、另一条五词，右补齐后三词样本应取自己的第三个有效位置，不能一律取第五位。使用左补齐时也要正确传入 attention_mask，检查位置编号和 cache_position；若 EOS 同时用作 PAD，要确认停止条件依据新生成的 token，而不会把输入侧补齐误判为完成。

这不是自回归模型在数学上只能左补齐。能按各条实际长度收集 logits、并正确管理位置与缓存的实现，也能支持右补齐；服务引擎还可能采用不补齐的变长布局。监督微调时则看注意力、标签和有效位置是否一致，不能把某个推理循环的经验当成所有训练与部署的硬规则。

#### 易错点

- 掩码屏蔽补齐位置作为键，不会自动改变生成循环取末位预测分数的索引。

<a id="inf-008"></a>
### INF-008 · temperature、top-k 与 top-p 如何影响生成？

**L1**

#### 答案

这三个参数都在调整下一 token 的候选分布。Temperature 把模型分数 z_i 除以温度 τ 后再做 softmax：τ 大于零时，温度越低通常越集中，越高越分散。零温度不能直接代入除法，而是由框架按贪心等特殊规则处理。Top-k 留下概率最高的固定 k 个候选，top-p 则按概率排序，取累计概率达到阈值的最小候选集合。

例如模型对一个问题很确定，top-p 可能只留下几个词；遇到开放续写、概率分散时，同样的 p 会留下更多词。它不是“只保留单个概率大于 p 的词”。过滤候选后要重新归一化，多种设置一起使用时，先调温度还是先过滤会改变最终结果，需按实际实现理解。

我会让可验证问答更偏稳定，创意生成适当保留多样性，再用任务样本调参。降低温度只能减少随机性，模型最确信的答案也可能是错的，因此不能保证没有幻觉。固定随机种子有助复现，但硬件、并行方式和数值差异仍可能改变结果，不能承诺跨环境逐 token 相同。

#### 易错点

- 零温度通常对应确定性解码，不保证答案真实或没有幻觉。
- Top-p 看排序后的累计概率，不是保留单个概率大于 p 的 token。

- 束搜索在开放生成中为什么可能复读？

<a id="inf-013"></a>
### INF-013 · 投机解码怎样保证目标模型的采样分布？

**L3**

#### 答案

投机解码用一个便宜的草稿模型先猜多个 token，再让目标模型一次并行验证这些位置，从而减少昂贵模型的串行轮数。它可以保持目标模型的采样分布，关键不是“猜对就用”，而是接受和纠正的概率规则。设同一前缀下目标分布为 p，草稿分布为 q，对从 q 采出的候选 x，以 min(1,p(x)/q(x)) 的概率接受。

首次拒绝后，后面的草稿全部丢弃，并从归一化的 max(p−q,0) 中采一个纠正 token；如果全部接受，通常还能从目标的下一位置分布多采一个。这样把草稿过多分配的概率纠正回来。拒绝时直接重新从 p 采样，再沿用同一证明是不成立的。这里的 p、q 必须是考虑温度、过滤和约束后的实际采样分布。

例如草稿与目标在普通句式上很接近，一次验证可能接受多个词；领域术语差异大时，接受率会下降。收益由草稿成本、接受率、验证开销和批大小共同决定，草稿越长不一定越快。还要协调 tokenizer、缓存和约束状态。分布一致不表示两次随机运行、甚至同一随机种子下的文本必然逐 token 一致；贪心版本也要按对应规则单独理解。

```math
\begin{aligned}a(x)&=\min\!\left(1,\frac{p(x)}{q(x)}\right)\\p_{\rm correction}(x)&=\frac{\max(p(x)-q(x),0)}{\sum_y\max(p(y)-q(y),0)}\end{aligned}
```

#### 易错点

- 标准投机采样用接受与修正规则保持目标分布，不是直接牺牲精度换速度。
- 分布一致不保证同一随机种子下文本逐 token 一致。

#### 追问

- 怎样根据接受率选择草稿长度？
- 贪心验证与随机采样验证的规则有什么区别？

### INF-031 · Greedy、Beam Search 与采样分别优化什么，beam 越大越好吗？

**L2**

#### 答案

贪心解码每一步选当前概率最大的 token，束搜索 Beam Search 则保留 B 条高分前缀，继续扩展后再筛选，近似寻找高概率的完整序列；采样从调整后的概率分布随机抽取，更适合需要多样性的输出。贪心只是局部选择，有限束搜索也不能保证找到全局概率最大的句子。

常见序列得分是各步条件概率的对数和，公式中的 y 是答案，x 是输入。由于对数概率通常为负，长答案累积后容易吃亏，于是会加入长度惩罚、EOS 规则或任务约束；示例的归一化用长度的 α 次方作分母。这些设置会改变搜索目标，不只是计算上的优化。

例如翻译的目标较明确，可以评估束搜索；开放写作更关注自然性与多样性，往往会选择采样。束更宽增加搜索覆盖，也增加缓存、重排和计算，并可能更偏爱重复或空泛的高概率文本，质量未必更好。流式束搜索还要管理候选公共前缀、终止和 KV 重排，候选顺序变化时缓存必须跟着变。最终应按任务质量、稳定性和成本选配置。

```math
S(y)=\sum_{t=1}^{|y|}\log p_\theta(y_t\mid x,y_{\lt t}),\qquad S_{\rm norm}(y)=S(y)/|y|^\alpha
```

#### 易错点

- 贪心每步选局部最高概率，不保证整句概率最大。
- 束更宽增加搜索与开销，不保证所有生成任务质量更高。

#### 追问

- 束搜索候选重排时，怎样同步对应的 KV 缓存？

<a id="inf-032"></a>
### INF-032 · LLM 为什么会复读或不停生成，重复惩罚应怎样正确使用？

**L2**

#### 答案

复读或不停生成，可能是模型陷入高概率循环，也可能是停止协议或推理实现出了问题。我会先区分回显输入、重复短语和没有正常结束，再检查训练时的 EOS、聊天模板、stop token、最大输出长度，以及 KV 与位置编号。然后在同一提示下比较贪心和采样，确认是否只有某种搜索策略会触发。

重复惩罚是补救手段，会改变模型分布。常见规则对出现过的 token 按分数符号处理：正 logits 除以 r，负 logits 乘 r，r 大于 1 时都降低相对概率；负数若也除以 r，反而更接近零、变得更有吸引力。Frequency penalty 按出现次数减分，presence penalty 只看出现过没有，禁止重复 n-gram 则是硬限制重复片段。

例如代码中的变量名、引用和专业术语本来就要重复，过强惩罚会破坏正确答案，所以要按任务回归。若根因是训练缺少终止样本、模板错配或缓存错误，调高温度并不能可靠修复。应优先纠正数据与协议，再适度调惩罚和预算；去掉复读也不代表事实正确。

```math
z_i'=\begin{cases}z_i/r,&z_i\gt 0\text{ and }i\text{ repeated}\\rz_i,&z_i\lt 0\text{ and }i\text{ repeated}\\z_i,&\text{otherwise}\end{cases},\quad r\gt 1
```

#### 易错点

- 重复惩罚需区分分数符号；负分除以大于一的系数反而会提高相对概率。
- 过强惩罚会误伤代码、引文和必要的重复术语。

#### 追问

- 按出现次数减分与只看是否出现过，对反复使用一个词有何差别？
- 如果模型没学会结束，增大温度为什么未必能修复？

### INF-034 · JSON Schema、正则或 CFG 约束生成如何实现，能否保证内容正确？

**L2**

#### 答案

约束解码是在生成每个 token 前，检查哪些候选还能继续组成合法结构，再把不允许的候选分数屏蔽。正则通常可转成有限状态机，嵌套 JSON 等结构需要上下文无关文法或等价的栈式处理；JSON Schema 还能限制字段类型和枚举。这里要按 token 对应的真实字节串推进状态，一个 token 可能含多个字符甚至不完整的 UTF-8 字节，不能简单按单字符过滤。

公式中的 s 是当前语法状态，A(s) 是允许的下一 token 集合，z_i 是原模型分数。过滤后只在 A(s) 内重新归一化，因此也改变了原采样分布。例如输出工具参数时，可以限定必须有名称和整数数量，比生成完再修 JSON 更直接。但保证取决于引擎支持的 Schema 子集、tokenizer 和完整终止，截断、取消或没有合法候选时必须返回显式失败。

格式正确不代表内容正确。合法 JSON 仍可能含错误事实、越界金额或无权限操作，应用层还要校验范围、业务一致性和权限。语法编译和每步掩码都有成本，可以缓存固定 Schema 与常用状态；我会同时测合法完成率、任务准确率和延迟，避免用“可解析”代替“可安全执行”。

```math
p'(i\mid s)=\frac{\mathbf1\{i\in A(s)\}\exp(z_i)}{\sum_{j\in A(s)}\exp(z_j)},\qquad A(s)\ne\varnothing
```

#### 易错点

- 格式合法不表示事实、业务或权限正确，不能直接执行。
- 一个 token 可能包含多个字符或部分 UTF-8 字节，不能只按单字符检查。

<a id="inf-005"></a>
### INF-005 · FlashAttention 的核心思想是什么，会改变注意力结果吗？

**L2** · 腾讯

#### 答案

FlashAttention 是一种更节省显存读写的精确注意力算法。普通实现往往把完整的注意力分数矩阵写到显存，再读出来做 softmax 和加权求和。序列越长，这个 T×T 的中间矩阵越大。FlashAttention 把 Q、K、V 分块搬进片上存储，算完一个块就累积输出，避免完整分数矩阵反复进出显存。

分块后仍需要对一整行分数做归一化，所以它会维护当前最大值、指数和与输出累计值。读到新块、行最大值改变时，要重新缩放旧的累计量，再合并新块；这样不保存所有分数，也能得到同一个数学上的 softmax。训练反向还可以重算部分中间量，以多一点计算换更少存储和读写。

它没有把稠密注意力的二次算术复杂度改成线性，也不是只看部分位置的近似稀疏注意力。浮点计算顺序改变后允许有小数值差异，不能保证逐位一致。收益取决于长度、数据精度、掩码、硬件和内核支持，短序列未必更快。KV Cache 则是复用历史键值、减少重复前向，两者解决不同开销，可以共同使用。

#### 易错点

- FlashAttention 减少中间存储和读写，稠密注意力的算术量仍是二次增长。
- FlashAttention 与 KV 缓存分别优化计算读写和历史重算，不能混为同一技术。

#### 追问

- 在线 softmax 合并两个块时为什么需要重缩放？

### INF-018 · torch.contiguous、stride、view 与 reshape 有什么关系？为什么影响推理？

**L2**

#### 答案

张量的 shape 只告诉我们逻辑尺寸，stride 告诉我们沿每个维度走一步，在底层存储中要移动多少元素。公式里的 storage_offset 是起点偏移，索引 i_j 乘第 j 维 stride 后相加，才得到真实存储位置。比如连续的 2×3 张量 stride 是 (3,1)，转置成 3×2 后通常变成 (1,3)，数据还在原来的地方，只是访问规则变了。

contiguous 会把不满足指定内存格式的张量复制为连续布局；已经满足时可以返回自身。view 只重解释兼容的 shape 和 stride，因此转置后直接展平可能报错。reshape 更宽松，能零拷贝时返回视图，不能时可能隐式复制，所以成功不代表免费。连续也要说清是默认格式还是 channels_last 等格式。

推理里拼接注意力头、转换 KV 布局或频繁转置大张量时，隐式复制会增加带宽、临时显存和启动成本。例如看起来只是 reshape，实际可能把整段长上下文缓存搬了一遍。我会根据下游内核的布局要求处理，并用性能分析器确认复制耗时；很多算子能读取非连续输入，不该每步无条件调用 contiguous。

```math
\mathrm{offset}(i_1,\ldots,i_n)=\mathrm{storage\_offset}+\sum_{j=1}^{n}i_j\,\mathrm{stride}_j
```

#### 易错点

- contiguous 可能复制数据，不是免费的形状操作。
- reshape 不保证零拷贝，连续性还要说明对应的内存格式。

- 为什么转置后 view(-1) 可能失败，而 reshape(-1) 可以完成？

### INF-033 · 算子融合、torch.compile 与 CUDA Graphs 分别降低什么开销？

**L2**

#### 答案

算子融合、编译和 CUDA Graphs 都可能加速推理，但主要减少的开销不同。融合把几个相邻操作合成较少的 GPU 内核，减少启动和中间张量读写。torch.compile 追踪计算图，针对形状生成或选择实现，并做图级优化。CUDA Graphs 则捕获一组 GPU 操作后重放，主要减少 CPU 调度与内核启动成本，尤其适合生成阶段很多很小的操作。

比如每 token 都要执行多次小算子，即使单算子很快，重复启动仍可能成为瓶颈，图重放就有价值。公式里的 N_launch 是启动次数，t_launch 是每次启动开销；重放把这部分换成一次图启动，但计算和访存仍要做。它不负责压缩 KV，也不会自动消除模型的数据依赖。

捕获通常需要地址和执行结构稳定，动态批大小或长度可用形状分桶、固定缓冲区或部分捕获，具体看框架支持。数据依赖控制流、CPU 同步、分配和图中断会影响收益；过度融合也可能提高寄存器占用，反而变慢。我会先确认瓶颈，再分别记录首次编译或捕获成本与预热后的性能，并检查真实形状分布、重编译次数、输出误差和显存增长。

```math
t_{\rm eager}\approx t_{\rm compute}+N_{\rm launch}t_{\rm launch}+t_{\rm memory},\qquad t_{\rm replay}\approx t_{\rm compute}+t_{\rm graph\ launch}+t_{\rm memory}
```

#### 易错点

- CUDA Graphs 减少调度和启动开销，不负责压缩 KV 缓存。
- 首次编译与预热后性能要分开，线上频繁重编译的成本也要计入。

#### 追问

- 形状分桶怎样取舍补齐浪费与计算图复用？

## 量化与稀疏推理

<a id="inf-009"></a>
### INF-009 · PTQ、QAT、W4A16 与 per-group quantization 是什么？

**L1**

#### 答案

量化是用更少位数近似表示权重或激活，以减少存储和搬运。PTQ 是训练完成后，用校准数据选择量化参数；QAT 是训练时把量化误差纳入过程，让模型适应低精度。W4A16 表示权重约 4 位、激活约 16 位，并不意味着所有算子都直接用 INT4 运算，实际可能需要反量化或保留部分高精度模块。

仿射量化把数值 x 除以尺度 s、舍入并加零点 z，再裁到整数范围；反量化用 s(q−z) 近似还原。Per-tensor 整个张量共享参数，per-channel 每个通道一组，per-group 每小组一组。更细粒度通常有利于控制误差，但会增加尺度、零点等元数据，也对内核提出要求。校准集要覆盖部署领域、输入长度和容易出现极值的场景。

例如小批量生成主要在读权重时，4 位权重可能明显减少带宽压力；大批量或 prefill 更受矩阵计算限制时，反量化和布局转换反而可能抵消收益。CPU 和 GPU 的指令及内核支持也不同。最后应在相同质量、长度和负载条件下测端到端延迟与吞吐。权重量化和 KV 缓存量化是两件事，模型文件变小也不等于服务总显存按同一比例下降。

```math
\begin{aligned}q&=\mathrm{clip}(\mathrm{round}(x/s)+z)\\\hat x&=s(q-z)\end{aligned}
```

#### 易错点

- 低位宽不一定更快，反量化和内核支持都可能影响收益。
- 权重量化与 KV 缓存量化是两项独立选择。

#### 追问

- 少数极大值为什么会增大量化误差？
- 怎样选择校准集，并验证任务精度损失？

<a id="inf-010"></a>
### INF-010 · GPTQ 为什么利用二阶信息进行逐层量化？

**L2**

#### 答案

GPTQ 是一种训练后权重量化方法，它关心的是量化后这一层的输出变了多少，而不只是每个权重舍入误差多大。给线性层一批代表性输入 X，原输出是 WX，量化后是 ŴX；即使两处权重误差相同，如果对应输入通道很活跃，对输出的影响也可能很不同。

它利用输入的二阶统计近似这种敏感性，逐列或逐块量化权重，并把已经引入的误差补偿到尚未量化的权重上。这样可以在控制离线计算成本的同时，比独立四舍五入更有针对性。二阶矩阵数值不稳定时需要阻尼，分组大小和处理顺序也会影响结果。这不是重新对整个底座做完整梯度训练。

与 AWQ 相比，GPTQ 主要通过层输出误差和二阶信息来安排补偿，AWQ 主要利用激活统计选择通道缩放。两者都依赖校准，也都是有损压缩。公平比较要固定位宽、组大小、校准数据和部署内核，分别检查任务质量与速度；尤其要回归长上下文、领域和多模态输入，不能把某个模型的近乎无损结果推广到全部场景。

#### 易错点

- GPTQ 是训练后量化，不是对整个底座重新做完整反向训练。
- 某个模型的近乎无损结果，不能推广到所有位宽和输入领域。

#### 追问

- 输入二阶矩阵数值不稳定时，为什么要加阻尼？
- 怎样在相同位宽、数据和部署条件下，与普通舍入比较？

<a id="inf-011"></a>
### INF-011 · AWQ 怎样保护重要权重，是否把 1% 权重保留为 FP16？

**L2**

#### 答案

AWQ 是激活感知的权重量化。它的出发点是：哪些权重值得重点保护，不能只看权重本身大小，还要看它连接的输入通道在真实数据中有多活跃。某个通道的激活较大，同样的权重量化误差就可能造成更大的输出偏差，所以用代表性输入统计寻找敏感通道。

它对选定通道的权重放大，同时把对应激活逆向缩小。浮点情况下两边相抵，线性层结果不变；但量化是离散舍入，这种重新分配动态范围可以减少关键通道的误差。尺度在离线校准中搜索，正式方法不需要完整梯度训练。论文中少量显著权重的讨论用于解释这个思路，不能说最终 AWQ 就是把 1% 权重一直留成 FP16；其方案考虑了统一低精度部署的硬件效率。

例如同是四位权重，有的层平均误差不大，但活跃通道被破坏后答案质量明显下降，AWQ 就针对这种敏感性。实际效果还受校准覆盖、分组和内核影响。我会验证业务准确率、长输入和异常输入，再测部署速度；既不能保证所有任务无损，也不能仅凭使用 AWQ 就承诺比 GPTQ 更快。

#### 易错点

- AWQ 对少量重要权重的分析，不等于最终把它们全部留成 FP16。
- AWQ 需要激活统计，不能只根据权重大小判断重要性。

#### 追问

- 为什么通道缩放能改变量化误差却不改变未量化输出？
- AWQ 与 GPTQ 的校准目标有何差别？

<a id="inf-012"></a>
### INF-012 · SmoothQuant 为什么把激活的量化困难迁移到权重？

**L2**

#### 答案

SmoothQuant 主要解决权重和激活都量化为 8 位时，激活中的极大值难以表示的问题。若某个输入通道偶尔远大于其他通道，共用一个量化尺度就会让普通值的分辨率变差。它用离线通道缩放，把一部分数值范围从激活搬到更容易处理的权重上，而不是直接忽略这些极大值。

在线性层 XW 中，X 是输入，W 是权重，S 是按输入通道定义的正对角缩放矩阵。把输入改成 XS⁻¹，权重改成 SW，乘积仍然等于 XW。可以理解为某列激活缩小几倍，对应权重行扩大几倍，浮点输出保持一致。尺度尽量吸收到相邻参数中，避免运行时增加很多额外操作。

但浮点等价不等于量化后没有误差，激活压小了，权重范围也被放大，需要平滑系数平衡两边。尺度和激活量化粒度要用代表性领域、长度进行校准，线上出现新的极值时仍可能退化。它主要面向 W8A8，而不是通常说的 W4A16；最终还要看硬件是否有合适的 INT8 内核，同时验证质量和实际延迟。

```math
XW=(XS^{-1})(SW)
```

#### 易错点

- 缩放前的浮点结果等价，不表示量化后没有误差。
- SmoothQuant 主要面向权重和激活都为八位的方案，不能一概称为 W4A16。

#### 追问

- 每个输入通道单独缩放激活，为什么不一定适合常规 INT8 矩阵乘法？
- 部署输入出现校准集没有的新极大值，应怎样处理？

<a id="inf-019"></a>
### INF-019 · 模型剪枝与量化有何区别，结构化、非结构化和 2:4 稀疏为何不一定加速？

**L2**

#### 答案

量化减少每个数的表示位数，剪枝减少连接、通道、头或层，两者可以组合。非结构化剪枝把任意权重置零，矩阵形状通常不变；结构化剪枝会真正缩小通道或删层；2:4 半结构化稀疏要求每组四个权重保留两个。公式里的 ρ 是权重零值占比，不是加速比；普通密集乘法依旧处理完整形状，所以“零了一半”并不意味着文件减半或速度翻倍。

剪什么也需要依据。幅值剪枝看权重大小，Wanda 的分数是权重绝对值乘对应输入通道的二范数，结合了真实激活；另一些方法用近似二阶敏感性。它们都是重要性估计，要用代表性校准数据验证。结构化方法还得处理模块依赖：删一个通道后，相关输入输出投影、残差维度和配置都要同步，不能只裁一个张量。恢复训练可能补回部分能力，但校准和训练都不能用最终测试集。

我会在相同质量和恢复训练预算下比较真实内存、延迟、吞吐及尾延迟。结构化剪枝更容易用密集内核，但缩成不适合硬件对齐的形状也可能更慢；不规则稀疏有索引和访存成本，2:4 则需要对应硬件、精度和内核支持。除了平均分，还要检查长上下文及少数关键能力，避免总体指标掩盖严重退化。

```math
\mathrm{score}_{ij}^{\rm Wanda}=|W_{ij}|\,\lVert X_{:,j}\rVert_2,\qquad\rho=1-\frac{\#\text{nonzero weights}}{\#\text{weights}}
```

#### 易错点

- 非结构化置零不自动缩小密集权重或计算量，50% 零权重也不保证速度翻倍。
- 结构化删通道时，相关投影、残差与配置必须同步，不能只裁一个张量。
