## 项目贡献与实验设计

<a id="prj-001"></a>
### PRJ-001 · 两分钟介绍 LLM/MLLM 项目，怎样讲清价值？

**L1**

#### 答案

围绕问题与约束、基线、关键方案、个人贡献、验证结果和局限，组织两分钟叙述。先说明用户或业务目标及原方案瓶颈，再解释选择，用可复现实验和有意义的基线证明改动。

结果说明指标口径、样本量、成本和测试条件，没有上线经历就明确离线实验范围。结尾准备一个关键失败案例和下一步，方便继续深挖；模型名称本身不能代替解决问题的过程。

#### 易错点

- 报相对提升却不给基线数值或指标定义。

#### 追问

- 你只保留一个改动，会保留什么，为什么？

<a id="prj-002"></a>
### PRJ-002 · 面试官追问“哪部分是你做的”，怎样给出可核验回答？

**L1**

#### 答案

明确团队分工和自己的模块，选一个从需求到实现、实验与故障修复的具体链路，讲清输入输出、设计决策和实现位置，能对应到代码、配置及实验记录。

区分开源已有能力、同事工作与个人贡献，准备一次独立发现问题、比较方案和验证结果的案例。对未参与环节说明了解程度；可以展示有权公开的脱敏材料，没有权限的公司资料则用结构和方法描述。

#### 易错点

- 把调用框架已有功能包装为独立研发全部能力。

#### 追问

- 如果让你从零重做该模块，你知道哪些隐藏依赖？

<a id="prj-003"></a>
### PRJ-003 · 为什么选这个模型，而不是更大的模型？

**L2**

#### 答案

把质量、时延、显存、成本、数据和许可约束列为可比较指标，在相同数据及预算下评测候选，覆盖真实场景的语言、长度、视觉细节和工具调用。

大模型可能质量更高但部署代价更大，小模型配检索或针对性训练也可能更合适。记录单位成功任务成本和满足 SLO 的吞吐，依据本任务测量选择，并说明场景或预算怎样变化会使决策改变；参数量和通用榜单不能单独决定方案。

#### 易错点

- 比较不同 prompt、不同上下文或不同采样设置后直接归因模型大小。

#### 追问

- 如果预算翻倍，你会优先换模型还是改数据？

<a id="prj-004"></a>
### PRJ-004 · 如何证明项目提升来自你的改动，而不是数据/算力增加？

**L2**

#### 答案

固定数据划分、训练预算和评测流程，逐模块消融，再测关键交互组合。事先明确假设与变动因素，记录失败实验；数据增加的版本补上同数据量对照，避免把数据或算力带来的增益归给结构。

同预算比较可以按 FLOPs、墙钟或数据量，但需说明公平性口径。重复不同种子或采用配对样本估计不确定性，同时报告成本、性能和切片退化；小样本下用置信区间辅助判断，不直接承诺显著提升。

#### 易错点

- 用“去掉模块后更差”证明机制成立，却不控制参数量与训练预算。

#### 追问

- 两个模块单独无效、合用有效时如何设计实验？

## 调试、数据与复现

<a id="prj-005"></a>
### PRJ-005 · 项目最困难的 bug，怎样避免答成“调参故事”？

**L2**

#### 答案

按可观察症状、可复现条件、候选根因、排除实验、修复和验证讲述。先给量化现象与出现时机，例如只在长序列或多卡出现，再构造最小复现，用断言检查 shape、数据、数值和同步。

用 padding mask 错位、标签 shift 等具体因果链解释现象；仅说学习率调小后变好，无法证明根因。验证修复及副作用，比较必要替代方案，并说明怎样加入监控和回归测试。

#### 易错点

- 把偶然相关当根因，无法解释为何改动生效。

#### 追问

- 如果 bug 无法稳定复现，你会保存哪些上下文？

<a id="prj-007"></a>
### PRJ-007 · 你会怎样把 badcase 转成下一轮训练数据？

**L2**

#### 答案

先分类错误来源，只有模型学习问题才直接进入训练候选；检索漏召回或工具故障优先修对应模块。为候选定义标签标准，去重并审核质量，覆盖正确回答和拒答场景，抽查标签一致性及类别平衡。

保留数据版本与来源，以时间或实体隔离避免相似问句泄漏到测试集。验证新错误是否修复，同时检查旧能力回归，防止只对少数 badcase 过拟合。

#### 易错点

- 把测试题原样加入训练，然后报告同一测试集提高。

#### 追问

- 错误样本稀少时，合成数据怎么验真？

<a id="prj-008"></a>
### PRJ-008 · 训练/评测实验怎样做到别人能复现？

**L2**

#### 答案

保存代码 commit、依赖版本、模型和数据 hash、完整配置、随机种子、硬件、有效 batch 及日志，给出从处理数据到评测的最小执行路径。Tokenizer、chat template、混合数据比例和 packing/mask 规则也属于复现条件。

恢复训练的 checkpoint 还应包含优化器、调度器与数据进度。固定 seed 不能保证跨设备或内核逐位一致，应说明环境差异，以数值容差或分布意义定义可接受的重现。

#### 易错点

- 只上传最终权重，没有数据处理脚本和评测命令。

#### 追问

- 恢复训练后 loss 跳变，首先检查哪些状态？

## 论文、视野与工程习惯

<a id="prj-006"></a>
### PRJ-006 · 介绍一篇论文，面试官最可能在哪些地方深挖？

**L2**

#### 答案

先说明问题、既有方法瓶颈、核心假设和目标函数，再介绍实现、关键对照实验与局限。准备推导一条关键公式、解释一个消融，以及更换假设后可能产生的影响。

评价 baseline 是否公平、数据是否污染、预算是否一致，区分作者报告的结果与自己的判断。没有复现就说明阅读范围，不编造实现经验或实验数字，也无需按论文段落逐一复述。

#### 易错点

- 只记住模型架构图和榜单分数，答不出损失与消融。

#### 追问

- 论文哪个假设在你的项目中不成立？

<a id="prj-009"></a>
### PRJ-009 · 遇到不会的模型或面试追问，怎样回答？

**L1**

#### 答案

先确认问题定义，说明确定的原理与不确定的版本细节，再给有条件的推理和验证方案。例如显存估算先区分训练与推理，列出权重、梯度、优化器状态、激活及缓存，再根据具体参数计算。

把条件写清，用数量级和守恒关系检查结果。被指出错误时修正推导，不把猜测包装成记忆事实，也不继续背与条件不符的结论。

#### 易错点

- 为显得熟悉而编造模型内部参数、论文结论或线上经历。

#### 追问

- 你需要哪些最小信息才能给出可信估计？

<a id="prj-010"></a>
### PRJ-010 · 技术方案有分歧时，如何推进决策？

**L1**

#### 答案

先确认双方优化的是同一个目标，例如质量、开发周期或运行成本，再把分歧转为可检验的目标与约束，列出候选、主要风险和决策期限，用小规模试验或已有数据比较。

约定最低质量、SLO 和决策责任，记录最终取舍及未解决假设，按分工执行，避免试验无限延长。面试回答用真实经历交代冲突、行动和结果；复盘聚焦证据，不套虚构的 STAR 数字。

#### 易错点

- 只说“听领导的”或“我说服了所有人”，没有证据与约束。

#### 追问

- 如果两个方案差异在置信区间内，你如何选择？

<a id="prj-011"></a>
### PRJ-011 · 面试中怎样说明 vibe coding 的实际用法、贡献和验证？

**L2**

#### 答案

把它描述为用自然语言驱动快速实现、迭代和探索的工作方式，并讲清具体工具、任务和结果。可先给需求、边界、接口和验收样例，让编码 Agent 查仓库、形成小改动、执行验证，再由开发者理解并审查 diff。不能仅把“用了某工具”“页面能打开”当作交付质量或个人技术贡献。

验证应针对行为而非复述生成代码：关键正常/异常路径、权限与数据边界、回归测试、依赖与配置、实际部署环境的集成检查。遇到测试失败要确认是实现问题、环境问题还是测试假设错，不让模型只为通过测试修改断言。代码生成可能带来不存在的 API、不安全实现或额外依赖，应核对项目实际版本和变化范围。

回答个人贡献时给出自己负责的需求分解、方案取舍、关键修正与验收证据，最好展示一次失败后如何定位并修复。衡量节省的时间也应包含阅读、调试和回归成本；使用 Agent 不免除理解最终代码和承担维护责任。

#### 易错点

- 把 Agent 写出的代码行数当作自己的技术深度或项目收益。
- 只让同一个生成模型自评正确，省略独立运行和审查。

#### 追问

- 如果 Agent 做出了超出需求的大重构，你怎样缩小改动并验收？
- 你能否不用工具解释最后交付的核心代码及其边界条件？
