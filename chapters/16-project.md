## 项目贡献与实验设计

<a id="prj-001"></a>
### PRJ-001 · 两分钟介绍 LLM/MLLM 项目，怎样讲清价值？

**L1** · 字节跳动 / 腾讯 / 小红书 / 阿里巴巴 / 百度 / 深势科技

#### 答案

我会先用一两句话说清项目解决谁的什么问题，以及质量、延迟、数据或成本约束。再说明原基线哪里不够，为什么选择当前方案，而不是只报模型名称。两分钟的主线是问题、基线、关键改动、自己负责的部分和验证。

例如文档问答项目，可以围绕“证据经常漏掉表格条件”展开，说明如何定位到解析或检索，比较过哪些方案，改动如何进入代码和实验。结果应来自真实日志与独立测试，交代指标定义、样本、基线、预算及部署条件；相对提升要有原值，只有离线实验就按离线范围讲。

最后我会说明关键边界，准备一个失败案例和下一步，使后续深挖能落到证据。如果只保留一个改动，选择依据应是消融和业务收益，不能凭听起来先进。没有做过的上线、数字和个人经历不补写，真实实验设计与局限本身就能说明判断能力。

#### 易错点

- 报相对提升却不给基线数值或指标定义。

#### 追问

- 你只保留一个改动，会保留什么，为什么？

<a id="prj-002"></a>
### PRJ-002 · 面试官追问“哪部分是你做的”，怎样给出可核验回答？

**L1** · 字节跳动 / 腾讯 / 小红书 / 阿里巴巴 / 快手

#### 答案

我会先讲团队分工，再明确自己负责哪个模块、输入输出和交付范围。贡献最好能对应到代码、配置与实验记录：哪项需求我拆解了，哪个方案我选择或否定了，哪个故障由我定位，最终怎样验收。

例如用了现成检索框架，可以如实说框架提供索引与调用，我负责文档规则、权限过滤、困难样本评测和故障修复；调用已有功能不能包装成独立实现全部算法。选一个从问题到实现、比较和验证的完整链路，比泛泛说“我负责模型优化”更可核查。

我会说明隐藏依赖，比如预处理、模型模板和服务版本，证明知道模块怎样运作。未参与环节明确了解范围，有权公开时展示脱敏材料，不能公开则说明结构与方法。没有真实案例时不能编贡献数字，面试中应围绕已有记录准备能经得起追问的内容。

#### 易错点

- 把调用框架已有功能包装为独立研发全部能力。

#### 追问

- 如果让你从零重做该模块，你知道哪些隐藏依赖？

<a id="prj-003"></a>
### PRJ-003 · 为什么选这个模型，而不是更大的模型？

**L2** · 腾讯 / 字节跳动 / 阿里巴巴 / 快手

#### 答案

我会先用目标任务的质量、延迟、显存、费用、数据、许可和维护约束解释模型选择，再展示同条件基线。更大、更新或榜单更高只是候选线索，不保证在中文、长输入、图表小字和工具调用上适合业务。

例如小模型配检索或针对性训练，可能在要求可引用的知识问答中更经济；大模型也可能减少失败和重试，最终应算每个成功任务成本及满足延迟目标的吞吐。直接用 API 与自部署同样要比较能力、接口、稳定性和所需训练：自部署有权重控制，但承担算力与运维，API 是否合适要看实际约束。

我会固定提示、信息、输出和采样预算，报告已经测过的结果，没测的候选说明待验证。预算增加后先依据错误结构决定换模型还是补数据和证据，而不是自动升级参数量。回答还应说明什么场景变化会改变选择，让方案体现取舍而不是维护某个模型名称。

#### 易错点

- 提示、上下文和采样不同，不能直接把结果差异归因于模型大小。

#### 追问

- 如果预算翻倍，你会优先换模型还是改数据？

<a id="prj-004"></a>
### PRJ-004 · 如何证明项目提升来自你的改动，而不是数据/算力增加？

**L2** · 小红书 / 阿里巴巴 / 字节跳动 / 美团 / 快手 / 深势科技

#### 答案

我会先写清假设和唯一变动因素，固定数据划分、评测、训练预算和解码，再做模块消融及关键交互对照。若新方案用了更多数据或训练时间，就补同数据量、同预算基线，不能把额外投入的效果全部归到结构改动。

例如两个模块单独没收益、合用有收益，应做四组：基线、只加 A、只加 B、A+B，再检查参数量和训练成本是否也改变。去掉模块后分数下降，只说明那组配置依赖它，未必证明声称的机制；还可用控制参数量、替代实现或机制相关样本进一步验证。

我会说明公平预算是 FLOPs、墙钟还是有效数据，必要时给多个口径，记录失败实验并重复种子或用配对样本估计差值区间。质量还要和成本、性能及重要分组一起报告。样本小或差异不稳定时，应讲观察与待验证假设，不能补造显著提升或把相关性说成因果。

#### 易错点

- 去掉模块后变差，不足以证明机制成立，还要控制参数量、数据和训练预算。

#### 追问

- 两个模块单独无效、合用有效时如何设计实验？

## 调试、数据与复现

<a id="prj-005"></a>
### PRJ-005 · 项目最困难的 bug，怎样避免答成“调参故事”？

**L2** · 腾讯 / 快手

#### 答案

我会按症状、复现条件、候选根因、排除实验、修复与验证讲 bug，而不是只说调低学习率后好了。先明确它什么时候出现，例如长输入、多卡或恢复训练后，再做最小复现，用数据、shape、掩码、数值和同步断言缩小范围。

如果是训练 loss spike，我会区分单个异常 batch、持续发散和日志归一化改变，保存附近样本 ID、长度、有效 token、学习率、梯度范数、溢出及恢复状态。用同一 checkpoint 和固定样本复现，再分别换 batch、检查标签错位和 token 归一化，或对疑似算子用 FP32 隔离数值问题。降低步长只能作为实验，不能自动证明根因。

损坏或极长数据可过滤限长，精度溢出要定位算子，调度与优化器恢复错误则修状态。修复后检查留出质量、副作用和复发，补对应回归与监控；曲线平滑不代表问题消失。难复现时也要保留完整环境、输入和事件顺序，面试中用真实记录说明排查，不能把偶然相关包装成确定因果。

#### 易错点

- 把偶然相关当根因，无法解释为何改动生效。

#### 追问

- 如果 bug 无法稳定复现，你会保存哪些上下文？

<a id="prj-007"></a>
### PRJ-007 · 你会怎样把 badcase 转成下一轮训练数据？

**L2** · 字节跳动

#### 答案

我会先给 bad case 归因，确定是否真是模型需要学习的问题。检索没找到资料、工具超时或模板错误，应先修对应环节，不能把所有错答直接丢进微调。进入训练的候选要有可信证据和标签标准，覆盖正确回答、拒答和必要恢复。

数据处理要去重、审核，检查标签一致性与类别平衡，并保留来源和版本。例如某一合同问题反复出现，可以扩展条件变体，但要验真，不能只让模型自己生成再自己认可。稀少错误可结合人工或规则验证合成样本，同时检查新答案是否真的被证据支持。

我会按时间、实体或文档分组，防止原测试题或近似问句进入训练后继续用同一题报提升。训练后看独立新样本是否改善，也回归旧能力，防止只记住几个 bad case。新增数据的价值要由泛化与成本证明，而不是看错误题背对了多少。

#### 易错点

- 把测试题原样加入训练，然后报告同一测试集提高。

#### 追问

- 错误样本稀少时，合成数据怎么验真？

<a id="prj-008"></a>
### PRJ-008 · 训练/评测实验怎样做到别人能复现？

**L2** · 美团 / 快手 / 深势科技 / 字节跳动 / 阿里巴巴

#### 答案

我会保存代码 commit、依赖、权重和数据 hash、完整配置、随机种子、硬件与日志，给出从数据处理到评测的最小执行路径。Tokenizer、聊天模板、数据混合、packing、掩码、有效 batch 和输出协议都属于实验条件，只有最终权重不够复现。

恢复训练还要保存优化器、调度器和数据进度；恢复后 loss 跳变，应先检查这些状态与学习率、采样和归一化是否一致。固定种子不能保证跨设备、内核逐位相同，因此要说明数值容差或重复运行分布上的可接受范围。

被问卡数、几千条数据多久训练或几步见效，我会先给真实记录，再解释模型、序列长度、图片分辨率、帧率帧数、micro-batch、梯度累积、数据并行规模和强化学习采样配置。“条数”不是有效 token 或视频成本。应拆采样、评分、训练与 I/O 耗时，报告预热吞吐、峰值显存和验证曲线。

开源参数只是起点，最终选择要有约束和消融。没有日志就给估算方法与待测项，不编卡数、耗时或最优超参数。把条件公开清楚，别人才能判断复现差异来自配置还是方法。

#### 易错点

- 只上传最终权重，没有数据处理脚本和评测命令。

#### 追问

- 恢复训练后损失跳变，应先检查哪些保存和恢复状态？

## 论文、视野与工程习惯

<a id="prj-006"></a>
### PRJ-006 · 介绍一篇论文，面试官最可能在哪些地方深挖？

**L2** · 阿里巴巴 / 腾讯 / 小红书 / 字节跳动 / 美团 / 快手 / 百度

#### 答案

我会先讲论文要解决的问题、已有方法的瓶颈、核心假设和目标函数，再讲模块怎样实现以及实验支持到哪里。准备解释一条关键公式中各项的作用、一个消融和一个失败边界，比按章节复述架构图更有用。

我会检查基线、数据、污染与计算预算是否公平，区分作者报告与我的推断。新模块是否损害预训练能力，要看初始化、哪些参数更新、目标收益和通用回归；能否扩到更大模型，需要跨尺寸、数据与预算对照，不能由一个小模型直接推断。未复现时只讲已读内容，不编实施经验和数字。

被问不改结构的替代方案，可以设计数据、提示或 RAG、蒸馏与参数更新对照，在相同信息和计算预算下检验。这样才能判断收益来自机制还是额外监督。若论文假设在项目中不成立，我会明确指出，并给验证方法；尚未做的实验用“我会比较”表达，不能讲成已有结果。

#### 易错点

- 只记住模型架构图和榜单分数，答不出损失与消融。

#### 追问

- 论文哪个假设在你的项目中不成立？

<a id="prj-009"></a>
### PRJ-009 · 遇到不会的模型或面试追问，怎样回答？

**L1**

#### 答案

我会先确认题目的定义和前提，把确定的原理与不确定的模型或版本细节分开。可以说清在什么条件下成立，再给推理与验证方式，而不是为了显得熟悉去补不存在的参数、论文结论或经历。

例如估算显存，要先问清训练还是推理、参数量、精度、并行方式、输入长度与 batch。训练还包含梯度、优化器状态和激活，推理主要还看 KV 与工作区；先给各项数量级，再用单位与守恒关系检查，不能只报一个记忆中的总数。

如果被指出错误，我会修正具体推导并说明结论如何变化；若缺少必要条件，就给条件化范围或最小验证实验。这样既不回避问题，也不把猜测包装成事实。面试准备时可以整理自己尚未验证的边界，但最终回答应以能解释和核查的内容为基础。

#### 易错点

- 为显得熟悉而编造模型内部参数、论文结论或线上经历。

#### 追问

- 你需要哪些最小信息才能给出可信估计？

<a id="prj-010"></a>
### PRJ-010 · 技术方案有分歧时，如何推进决策？

**L1**

#### 答案

我会先确认双方优化的是同一个目标，把“哪种技术更好”转成可测约束，例如质量底线、延迟、成本和交付期限。然后列候选及关键假设，用已有数据或小规模对照解决最影响决策的不确定性。

例如两个模型效果差异落在置信区间内，可以在满足质量底线的前提下比较费用、运维和可逆性，选择更容易维护或后续切换的方案，同时记录差异仍待验证。不是每个争论都要无限试验，应明确决策负责人、最晚时间和后续复查条件。

我会记录取舍和未解决风险，按分工执行，再用上线或实验反馈复盘。面试讲真实经历时，说明实际分歧、我做的验证与结果，不能编一个说服所有人的故事或虚构 STAR 数字。证据、约束和合作过程比“最后听谁的”更能体现工程判断。

#### 易错点

- 只说“听领导的”或“我说服了所有人”，没有证据与约束。

#### 追问

- 如果两个方案差异在置信区间内，你如何选择？

<a id="prj-011"></a>
### PRJ-011 · 面试中怎样说明 vibe coding 的实际用法、贡献和验证？

**L2**

#### 答案

我会把 vibe coding 解释为用自然语言驱动快速实现与迭代，再说明自己怎样把需求、边界、接口和验收交给编码 Agent。让它查项目、提出小改动、执行检查后，我仍要读懂差异并决定是否符合需求，不能用工具名称、代码行数或页面能打开代替质量和贡献。

验证针对实际行为：正常异常路径、权限和数据边界、历史回归、依赖配置及部署集成。API 是否存在要查项目真实版本，测试失败要区分实现、环境和测试假设，不能让模型为了绿灯删断言。若生成了超范围重构，就缩小到必要修改，再重新验收。

回答个人贡献时，我会给真实的需求分解、方案取舍、关键修正和验收证据，准备解释核心代码与边界，最好用一次实际失败的定位展示判断。节省时间要算阅读、调试和回归成本，不能只算生成速度。同一个模型自评正确也不足以交付，独立运行与审查必不可少，使用 Agent 不免除维护责任。

#### 易错点

- 把 Agent 写出的代码行数当作自己的技术深度或项目收益。
- 只让同一个生成模型自评正确，省略独立运行和审查。

#### 追问

- 如果 Agent 做出了超出需求的大重构，你怎样缩小改动并验收？
- 你能否不用工具解释最后交付的核心代码及其边界条件？
